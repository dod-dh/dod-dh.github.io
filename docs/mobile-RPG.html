공개 범위 안내 — 이 문서는 외부 공개를 전제로 작성했다. 내부 클래스·함수·파일 식별자, 저장 파일 경로, 패키지/서명 정보, 서버 연동 예정 구성, 개발용 디버그·튜닝 기능은 역할 명칭으로 일반화하거나 생략했다. 구조와 의사결정, 계측 결과는 실제 그대로다.

1. 배경과 설계 목표

방치형 RPG는 겉보기에 단순하지만, 실제로는 "수치가 서로 물려 있는 시스템" 이다. 성장 축이 8개(레벨업 flat · 골드 구매 % · 스킬 · 장비 · 칭호 · 환생 누적 · 종족 진화 · 신념)이고, 이들이 곱연산/합연산 규칙에 따라 최종 데미지에 합류하며, 그 결과가 다시 스테이지 진행 속도 → 획득 재화 → 성장 속도로 되돌아온다. 여기서 두 가지 문제가 생긴다.

  1. 손으로 플레이해서는 밸런스를 검증할 수 없다. 목표 페이스가 400일이 넘는 게임이다.
  2. UI를 띄워야만 로직을 돌릴 수 있으면 아무것도 자동화할 수 없다.

그래서 프로젝트의 1번 설계 목표를 이렇게 잡았다.

게임 규칙 전체를 화면 없이 실행할 수 있어야 한다.

이 한 줄이 Clean Architecture 채택, 데이터 외부화, 헤드리스 툴체인까지 전부를 끌고 왔다. 아키텍처가 목적이 아니라, 시뮬레이션 가능성이 목적이고 아키텍처가 수단이었다.

부차 목표는 다음과 같았다.

  • 밸런스 수치를 코드 재컴파일 없이 바꿀 수 있을 것
  • 저장 방식을 로컬 → 서버로 바꿔도 게임 규칙과 화면이 무변경일 것
  • 혼자 개발하므로, 6주 전에 내린 결정의 이유를 6주 뒤의 내가 알 수 있을 것

2. 아키텍처 결정

2.1 레이어와 의존 방향

Presentation ──► Application ──► Domain
      │                              ▲
      └──────────────────────────────┘ (직접 호출 금지)
                     Infrastructure ──┘ (인터페이스로 역전)
  • Domain — 게임 규칙. Godot 노드를 상속하지 않는 순수 클래스로만 구성했다. 씬 트리·타이머·시그널을 쓰지 않으므로, 시간 진행은 언제나 호출자가 델타를 넘겨주는 방식이다. 이 제약 하나로 "실시간 게임 루프"와 "1틱 = 0.1초로 수만 틱 돌리는 시뮬레이터"가 같은 코드를 쓴다.
  • Application — 유스케이스 59개. "한 가지 사용자 의도" 단위로 쪼갰고 (전투 진행 / 스탯 구매 / 장비 승급 / 던전 입장 / 우편 수령 …), 도메인별 8개 폴더로 묶었다. 유스케이스는 신규 로직을 거의 갖지 않고 검증 → 도메인 호출 → 저장만 조합한다.
  • Infrastructure — 저장소 구현과 합성 루트. Godot에는 DI 컨테이너가 없어서, 앱 시작 시 단 한 곳에서 저장소를 만들고 그것을 주입해 유스케이스를 조립한다. 화면은 조립된 유스케이스만 보고, 저장소 구현체의 존재를 모른다.
  • Data — Resource 스키마와 enum. 밸런스 수치가 담기는 그릇이다.

2.2 왜 유스케이스를 59개나 만들었나

작게 쪼갠 이유는 테스트 단위를 만들기 위해서다. 헤드리스 검증 스크립트는 화면 없이 유스케이스를 직접 호출해 결과를 단정한다. 유스케이스가 크면 검증도 "화면을 띄워야만 되는 것"이 되어버린다.

부수 효과로, 같은 규칙을 두 경로가 공유해야 할 때 재사용이 쉬웠다. 예를 들어 던전 소탕(전투 생략)과 던전 클리어(실제 전투)는 보상 지급 로직을 공유한다 — 보상 규칙을 두 번 적으면 한쪽만 고쳤을 때 조용히 갈라지기 때문이다.

2.3 교체 지점을 미리 만들어 둔 곳

| 교체 예정 | 현재 | 교체 시 영향 범위 | |---|---|---| | 저장소 | 로컬 파일 직렬화 | Infrastructure 구현체 1개. 도메인·화면 무변경 | | 광고 / 결제 | 미연동 (호출 지점만 유스케이스로 확보) | Infrastructure에 구현체 추가 | | 종족 추가 | 데이터 2종(종족·스킬트리) | 코드 변경 없음 |

3. 도메인 설계 하이라이트

3.1 엔티티와 계산기의 분리

캐릭터 엔티티는 상태만 보관하고, 최종 스탯 산출은 인자를 받아 결과를 돌려주는 순수 계산 모듈이 담당한다. 이 분리가 만든 실질적 이득:

  • 화면과 시뮬레이터가 같은 함수를 부른다 → 표시값과 실제 전투값이 갈라질 수 없다
  • 계산기에 입력을 조작해 넣으면 "장비를 끈 상태", "칭호를 끈 상태" 같은 가상 조건을 코드 수정 없이 만들 수 있다 → 기여도 분해 계측이 가능해졌다

전투 상태도 같은 원칙으로 갈랐다. 계정 데이터를 담는 캐릭터 엔티티에는 "현재 체력" 개념이 없다. 전투 중에만 존재하는 체력·버프는 전투 전용 엔티티가 따로 갖고, 전투 상태 객체가 이 둘을 묶는다. 덕분에 전투가 끝나면 전투 상태만 버리면 되고, 계정 데이터가 전투 중간 상태로 오염되지 않는다.

3.2 데미지 파이프라인 — 합연산과 곱연산의 규칙화

성장 축이 8개라 "이 보너스는 어디에 더해지는가"가 가장 큰 혼란 요인이었다. 그래서 스탯 종류별로 합류 규칙을 명시적으로 고정했다.

공격력 · 방어력 · 체력      : 곱연산  ×(1 + 보너스%)
크확 · 크뎀 · 회피 · 명중   : 합연산  (%p를 값 자체에 가산)
"최종 데미지 증가"          : 소스별 개별 곱연산  ∏(1 + %ᵢ)

최종 데미지 증가에 합류하는 소스는 환생 누적 · 종족 진화 · 특정 패시브 · 상태이상(넘어짐) · 스킬 고유 조건부 보너스로, 전부 독립 곱연산이다. 합연산으로 두면 후반에 한 소스가 전체를 지배하고, 곱연산으로 두면 각 축이 끝까지 의미를 갖는다.

확률형 스탯(크리티컬 확률 · 회피 · 명중 · 관통)은 누적치가 100%를 넘어가므로 clamp 규칙과 초과분 전환 규칙(크리티컬 확률 100% 초과 → 슈퍼크리티컬)을 계산기에 넣었다. 이 지점이 전투 계산 검증의 핵심 포인트라서 별도 검증 스크립트를 두고 있다.

3.3 다중 대상 원형 전투

초기에는 몬스터 1마리 FIFO 모델이었다. 현재는 일반 스테이지에서 최대 10마리 동시 교전이고, 몬스터는 360° 사방에 균등 배치되어 전투 슬롯까지 걸어 들어온다.

여기서 나온 설계 규칙들:

  • 이동 중에도 피격되지만, 몬스터는 도착해야 공격한다 — 접근 시간(3~4초)이 밸런스 상수다
  • 평타는 사거리 안 최근접 1마리, 스킬은 사거리 안 최근접 N마리를 독립적으로 타격한다 (배열 순서 기준이 아니다 — 원형 배치에서는 순서가 거리와 무관하다)
  • 스턴/넘어짐으로 몬스터가 공격을 못 할 때는 타이머를 멈추지 않고 공격 턴을 소비(스킵) 시킨다. 타이머를 멈추면 CC가 풀리는 순간 즉시 때리는 "CC 후 즉발"이 된다
  • 몬스터는 명중/회피/크리티컬을 갖지 않는 비대칭 설계다. 플레이어만 스탯 시스템 전체가 적용된다 — 몬스터에 확률 스탯을 주면 곡선 캘리브레이션에 분산이 하나 더 늘어나기 때문이다

이 변경은 밸런스에 큰 파장을 남겼다. 1마리 모델은 피격량을 마릿수만큼 과소평가하고 스킬의 다중 대상 가치를 통째로 낭비해서, 페이스를 2.6배 과소평가하고 있었다.

3.4 파생값을 저장하지 않는다

세이브에는 원본 사실만 담는다.

| 저장하는 것 | 저장하지 않는 것 (로드 후 재계산) | |---|---| | 레벨 · 경험치 · 재화 · 환생 횟수 | 환생 누적 보너스 (환생 횟수에서 파생) | | 골드 구매 횟수 | 레벨업 flat 성장분 (레벨·환생 횟수에서 파생) | | 스킬 노드 레벨 · 슬롯 배치 | 장비 합산 보너스 · 칭호 합산 보너스 (파생 캐시) | | 장비 인스턴스 · 슬롯 강화 | 최종 스탯 전량 |

이유는 용량이 아니라 규칙의 단일화다. "환생하면 초기화되는 값"을 저장해버리면, 초기화 규칙을 도메인과 저장 코드 두 곳에서 지켜야 한다. 저장하지 않으면 초기화 규칙이 파생 공식 하나에만 존재한다.

다만 파생 캐시에는 복원 순서 제약이 생긴다. 장비 보너스 캐시는 오프라인 보상 계산보다 먼저 복원돼야 한다 — 비어 있는 채로 계산하면 "장비 없는 전투력"으로 처치 속도를 추정해 보상이 과소 지급된다. 이런 순서 의존은 주석이 아니라 조립 순서 자체로 고정했다.

3.5 규모가 커지는 시스템을 다루는 법 — 칭호 166종

칭호는 개수가 많고 조건 축이 14가지가 넘는다. 두 가지 결정으로 관리 비용을 눌렀다.

  1. 조건을 단일 규칙으로 통일 — 전 칭호를 "진행값 >= 임계값" 한 가지 형태로 환산했다. 조건 종류마다 판정 코드를 두면 166개가 166가지 버그 표면이 된다.
  2. 전역 배수를 집계 시점에 한 번만 곱한다 — 개별 칭호 데이터에는 기준값만 두고, 스케일 조정은 배수 2개로 끝낸다. 166개 파일을 개별 수정하지 않고 재캘리브레이션이 된다.

또한 "값이 0이라 미달"과 "시스템이 아직 없어 판정 불가"를 구분한다. 랭킹 조건은 서버가 없어 판정 자체가 불가능하고, 게다가 "작을수록 좋음"이라 일반 규칙과 반대다. 이 구분을 도메인이 소유하고 화면은 그대로 표시만 한다.

계정 누적값 16종은 한 곳에서만 갱신한다 — "이 값이 언제 오르는가"를 한 파일로 모으기 위해서다.

3.6 장비 — 교체 페널티를 없앤 설계

  • 슬롯 강화는 장비가 아니라 슬롯에 귀속된다. 상위 등급 장비로 갈아탈 때 강화가 날아가지 않으므로 "좋은 장비를 먹었는데 갈아타면 손해"라는 방치형의 고질적 역인센티브가 사라진다.
  • 승급·제작·성급·리롤은 전부 제자리 변환이다. 인스턴스 참조가 유지되므로 장착 중에도 가능하고, 화면이 선택 상태를 인덱스가 아니라 참조로 들고 있어도 안전하다.
  • 슬롯 1개분 기본 스탯을 단독 계산하는 진입점을 따로 뒀다 — 집계와 화면이 반드시 같은 식을 쓰게 하기 위한 것으로, 화면에서 재계산하면 공식이 이중 정의된다.

3.7 오프라인 보상

"경과 시간만큼 전투를 실제로 돌리는" 방식은 8시간치를 시뮬레이션해야 해서 쓸 수 없다. 대신 실측 처치 속도 + 해석적 진행 방식을 택했다.

  1. 현재 스펙으로 몬스터 1마리를 잡는 데 걸리는 시간을 실제 전투 로직으로 측정한다
  2. 상한 시간과 효율(데이터로 관리)을 적용한 경과 시간을 처치 수로 환산한다
  3. 그 수만큼 실제 처치 보상 유스케이스를 반복 호출해 경험치·레벨업·스테이지 클리어를 연쇄 반영한다

핵심은 3번이다. 별도 근사식을 쓰지 않고 실제 보상 경로를 재사용하므로, 온라인 보상 규칙이 바뀌면 오프라인 보상도 자동으로 따라온다. 처치 속도 측정 모듈은 던전 보상 계산과도 공유한다.

"마지막 접속 시각"은 별도 필드를 만들지 않고 세이브 파일의 저장 시각을 재사용했다 — 두 개를 두면 둘이 어긋나는 순간이 반드시 온다.

4. Presentation 설계

4.1 앱 쉘 + 중앙 뷰 교체

화면 전환(씬 체인지)도, 전체 모달도 쓰지 않는다. 앱 쉘 하나가 상시 살아 있고 중앙 영역만 교체된다.

앱 쉘
├ 배경
├ 콘텐츠 루트        ← 여기만 교체 (모달도 이 안에서 뜬다)
├ 상단 HUD           플로팅 — 프로필 · 재화 · 메뉴
├ 좌측 레일          플로팅
├ 퀘스트 카드        플로팅 — 스테이지 / 일일 미션
├ 하단 네비게이션    고정
└ 플라이아웃 메뉴    탭 위로 상승

핵심은 자동 전투 세션의 소유권이 쉘에 있다는 점이다. 전투 뷰는 매 틱 결과를 받아 렌더링만 하고, 세션 전진은 쉘의 프레임 루프가 담당한다. 전투 뷰가 세션을 굴리게 만들면 성장 화면을 여는 순간 방치 진행이 멈춘다 — 방치형에서는 치명적이다.

모달도 콘텐츠 루트의 자식이라 상단바·하단 메뉴를 가리지 않는다. 전체를 덮는 오버레이로 남긴 것은 둘뿐이다: 임시 드롭다운과 환생 확인 (되돌릴 수 없는 동작이라 확인을 유지).

4.2 뷰 공통 계약

새 화면을 붙이는 비용을 낮추기 위해 뷰가 지켜야 할 계약을 3개로 고정했다.

| 계약 | 내용 | |---|---| | 초기화 | 캐릭터 · 종족 데이터 · 세션을 받는 동일 시그니처. 쓰지 않는 인자는 무시한다 (뷰마다 시그니처가 다르면 쉘이 분기를 갖게 된다) | | 프레임 갱신 | 선택 사항. 전체 재구성이 위험한 뷰는 의도적으로 두지 않거나 경량 경로만 구현한다 | | 상태 변경 | 뷰가 세션·씬을 직접 만지지 않고 시그널로 쉘에 올린다 |

두 번째 항목에는 실제 사고가 배경에 있다. 뷰를 매 프레임 전체 재구성하면 버튼 탭이 유실된다. 그래서 어떤 화면은 재화·버튼 활성만 갱신하고, 어떤 화면은 프레임 갱신 자체를 두지 않는다.

메뉴 등록도 데이터화했다. 뷰 레지스트리 한 곳이 "키 → 제목·아이콘·씬·모달 여부"를 소유하고, 탭 구성이 별도 테이블을 소유한다. 새 메뉴 추가 = 항목 하나 + 키 하나이고, 씬 경로가 비어 있으면 자동으로 "준비중" 자리표시가 뜬다.

4.3 테마 토큰화

레이아웃은 대부분 코드로 동적 생성한다(씬 파일은 쉘·전투 뷰·재사용 위젯만). 색·크기·스타일 빌더는 테마 모듈에 static 헬퍼로 모아 중복을 없앴다.

다크 → 라이트 팔레트 전환 때 얻은 교훈이 여기에 반영돼 있다: 한 색 토큰이 두 역할을 겸하면 팔레트를 바꾸는 순간 조용히 깨진다. "패널 배경"과 "강조 버튼 위 글자색"이 같은 상수를 쓰고 있어서, 값 하나를 바꾸자 버튼 글자가 사라졌다. 어두운 딤 위에 그려지는 라벨도 본문 글자색이 잉크로 바뀌면서 검은 딤 위 검은 글자가 됐다.

지금은 역할별 토큰으로 분리했고, 버튼 글자색은 배경 밝기에서 자동으로 고르는 헬퍼가 정한다 — 호출 지점마다 손으로 정하면 반드시 몇 군데를 놓치기 때문이다.

4.4 큰 수의 표기

방치형은 후반 수치가 무한정 커진다. 표시용 축약 표기를 스프레드시트 열 이름과 같은 이중 문자 확장(1=A … 26=Z, 27=AA …)으로 구현해 상한을 없앴다. K/M/B/T 방식은 준비한 단위가 떨어지는 순간 표기가 깨지지만, 이 방식은 자릿수가 아무리 늘어도 짧게 유지된다. 화면에 나오는 모든 큰 수치가 이 하나의 포매터를 경유한다.

4.5 안전영역

화면을 기기 끝까지 그리도록 바꾸면서 노치·펀치홀·제스처바 대응이 필요해졌다. 설계 규칙은 "여백은 쉘이 소유하고 위젯에 나눠 준다" 이다 — 위젯은 안전영역의 존재를 모른다.

안전영역 값 읽기(플랫폼 의존)와 여백 환산 계산(순수 함수) 을 분리해, 계산부는 헤드리스로 검증할 수 있게 만들었다. 값 자체는 모바일에서만 신뢰한다 — 데스크톱에서는 창과 무관한 값이 돌아온다.

4.6 아트 폴백

캐릭터 표현 리소스는 씬·데이터에 텍스처를 박지 않고 경로 규약 + 지연 로드로만 다룬다. 정의가 없는 조합은 빈 값을 돌려주고 호출 측이 폴백한다 — 에셋이 없거나 깨져도 화면이 죽지 않는다. 개발 초기에 이모지로 대체하던 흔적이 지금은 최종 폴백 경로로만 남아 있다.

5. 연출과 도메인의 동기화

방치형 전투 연출에서 가장 어려운 부분은 "연출이 도메인 사실과 어긋나지 않게 하는 것" 이었다.

5.1 재현이 아니라 관측

초기 구현은 전투 뷰가 자체 타이머로 공격 주기를 재현했다. 문제는 전투가 뷰와 무관하게 계속 진행된다는 점이다 — 다른 화면을 보다 돌아오면 뷰 타이머와 도메인 타이머의 위상이 영구히 어긋났다.

지금은 도메인의 공격 타이머가 감소 후 리셋되는 것을 관측해서 연출을 낸다. 연출은 도메인 사실의 종속 함수이지, 병렬로 도는 두 번째 시계가 아니다.

5.2 타격 프레임 정렬

관측한 그 틱에 이펙트를 내면 칼을 치켜들기도 전에 검흔이 먼저 나간다(공격 애니메이션 0번 프레임). 그래서 관측 시점에는 대상 좌표만 붙잡아 두고, 스프라이트 모션 데이터가 선언한 타격 프레임을 지나는 순간에 발사한다. 캐릭터의 타격 판정과 이펙트가 같은 신호를 나눠 쓰는 구조다.

여기에 안전장치를 하나 더 뒀다. 스킬이 공격 모션을 끊어 타격 프레임을 영영 지나지 않는 경우가 있어, 공격 간격 마감을 함께 둔다 — 불변식은 "평타 1발 = 검흔 1발"이다.

5.3 도메인이 알려주는 것만 그린다

  • 데미지 숫자는 도메인이 반환하는 이벤트 목록(대상 · 수치 · 크리티컬 여부)만 보고 그린다. 단, 처치된 몬스터의 마커는 그 프레임에 즉시 정리되므로 팝업 좌표는 정리 전에 캡처해야 한다 — 안 그러면 즉사 타격의 팝업이 위치를 잃는다.
  • 스테이지 전환 연출(약 1.8초) 동안은 세션을 전진시키지 않는다. 대신 필드 스크롤과 걷기 모션은 따로 굴린다 — 안 굴리면 땅만 흐르고 캐릭터가 한 프레임에 굳는다. 또 도메인은 클리어와 같은 틱에 다음 무리를 스폰하므로, 전환 시작 시 화면의 마커를 치워야 "다음 스테이지 몬스터가 처음부터 다 모여 있는" 그림이 되지 않는다.

5.4 이펙트 파이프라인

평타 검흔은 커스텀 셰이더로 그린다. 텍스처는 종족별 원화에서 오프라인 파이프라인으로 굽는데, 그 과정이 그 자체로 하나의 문제였다 — 8.7절 참조.

스킬 연출은 아키타입 8종으로 유형화했다. 스킬마다 연출을 따로 만들면 확장이 선형으로 비싸지므로, 형태 축으로 나누고 색·크기·타이밍만 데이터로 준다.

전투 캔버스에는 z 계층 규약을 뒀다. 배경 / 몬스터 / 이펙트 / 오버레이가 각각 자기 대역을 갖고, 검증 스크립트가 그 불변식을 지킨다 — 렌더 결과만 봐서는 "가려진 것"과 "원래 없는 것"이 구분되지 않는다.

6. 툴체인과 품질 관리

유닛 테스트 프레임워크를 도입하는 대신, 엔진 CLI를 테스트 러너로 쓰는 체계를 만들었다. 전체 개발 코드의 37%(16,074줄)가 여기에 들어갔다.

| 종류 | 개수 | 실행 방식 | 무엇을 잡는가 | |---|---|---|---| | 헤드리스 검증 | 33종 | 렌더링 없이 도메인·유스케이스를 직접 호출해 단정 | 로직 회귀 · 데이터 정합성 · 규칙 위반 | | 렌더 캡처 하네스 | 23종 | 실제 렌더링 후 PNG 저장 | 레이아웃 넘침 · 겹침 · z-order · 잘림 | | 오프라인 이미지 파이프라인 | 21종 (Python) | 원화 → 게임 에셋 변환 | 에셋 가공의 재현성 | | 밸런스 시뮬레이터 | 1종 | 수백 일 분량 플레이 전개 | 페이스 · 정체 원인 · 성장 기여도 | | 전 스크립트 일괄 파싱 | 1종 | 전 스크립트를 문법 검사만 수행 | 실행되지 않는 경로의 문법 오류 |

6.1 헤드리스 검증이 가능한 이유

도메인이 씬 트리를 쓰지 않기 때문이다. 검증 스크립트는 엔진을 헤드리스로 띄우고 유스케이스를 직접 호출해 결과를 단정한다. 부수 효과로, 헤드리스 실행 자체가 전 스크립트를 로드하므로 파싱 에러 전수 검사도 겸한다.

검증 대상의 예:

  • 동시 처치가 클리어 조건을 넘겼을 때 보상은 지급되고 처치 기록은 넘치지 않는가
  • 미리보기에 표시한 값과 실제 적용값이 같은가 (강화 · 승급 · 분해 · 리롤 전 탭)
  • 버튼 활성 판정이 유스케이스 성공 여부와 일치하는가 (부족 사유까지 구분, 부분 차감 없음)
  • 원형 전투의 거리 불변식 — 정지 거리 < 평타 사거리 (어기면 교착), 사방 스폰 균등성
  • 스프라이트 한 세트 안에서 프레임 크기가 전부 같은가 (다르면 캐릭터가 튄다)
  • 같은 등급 장비가 연속 배치될 때 일괄 분해에서 누락이 없는가 (인덱스 밀림 함정)

6.2 화면은 캡처로 검증한다

헤드리스는 렌더링을 하지 않으므로 UI는 검증할 수 없다. 그래서 특정 씬만 띄워 PNG로 저장하는 하네스를 만들었고, 데이터가 있어야 보이는 화면은 픽스처를 주입한다.

특히 플레이해서는 볼 수 없는 화면이 있다. 오프라인 보상 모달이 그렇다 — 개발 PC에서는 창을 최소화해도 게임이 계속 돌아 오프라인 상태가 만들어지지 않는다. 결과 데이터를 픽스처로 넣어 그리는 전용 하네스를 뒀다.

또한 캡처 창은 모니터 작업영역보다 커질 수 없어서 세로로 긴 폰 화면비를 만들 수 없다. 요청한 해상도를 줘도 창이 잘려 나오므로, 서브뷰포트를 써서 모니터 제약 없이 원하는 캔버스 크기를 만드는 공용 모듈로 해결했다.

6.3 도구에도 규약을 세웠다

이름만 보고 성격을 알 수 있게 접두어 규약을 정했다.

| 접두어 | 모드 | 성격 | |---|---|---| | verify_* | 헤드리스 | 로직 · 데이터 검증 (커밋 보존) | | capture_* | 렌더 | 화면 캡처 (씬 동반) | | _verify_* | 헤드리스 | 일회성 자체 테스트 (검증 후 삭제, 커밋하지 않음) | | Python 도구 | 오프라인 | 이미지 가공 · 전 스크립트 파싱 |

7. 밸런스 엔지니어링

가장 많은 시간을 쓴 영역이고, 가장 배운 게 많은 영역이다.

7.1 시뮬레이터가 실제 도메인을 재사용한다

밸런스 시뮬레이터는 별도의 수식 모델이 아니다. 실제 전투 유스케이스, 실제 보상 계산기, 실제 스킬 레벨업 검증기·비용 계산기를 그대로 호출해 "처치 → 경험치 → 레벨업 → 골드 → 스탯 구매 → 스테이지 진행 → 환생"을 시간 스텝으로 전개한다.

시뮬 전용 수식을 두면 규칙이 갈라진다. 실제로 과거 두 번 시뮬이 요구경험치·보상·비용을 직접 계산하던 시기가 있었고, 그때마다 게임과 다른 곡선을 캘리브레이션했다. 지금은 시뮬이 상수를 리소스에 밀어넣기만 하고, 계산은 전부 도메인에 위임한다. 그리고 시뮬 상수와 데이터 파일의 일치를 강제하는 정합성 검증 스크립트를 따로 뒀다.

7.2 목표에서 곡선을 역산한다

19개 대스테이지 각각의 도달 시점과 환생 횟수를 목표로 고정하고(총 415.5일 / 환생 80회 · Lv1000), 시뮬 출력과의 배수를 목적 함수로 삼아 노브를 조정하는 방식이다.

하루 유효 플레이 = 온라인 2h + 오프라인 8h × 80% = 8.4h/일
기준점 고정      = 1-1 몬스터 HP 100 / 공격력 10 / 드랍골드 100 / 드랍EXP 10
스테이지 구조    = 19대 × 20단 = 380단, 보스는 대스테이지 끝 1회

노브는 셸 인자로 오버라이드할 수 있게 만들어, 파일 편집 왕복 없이 루프를 돌린다. 1회 실행이 10분을 넘길 수 있어 조기 종료 지점도 인자로 준다.

7.3 핵심 발견 — 노브는 순서 의존이다

착수 시점 실측은 목표 415.5일 대비 7.2일(×0.02) 이었다. 몬스터 체력 곡선을 27배 올려도 페이스가 거의 변하지 않았다. 원인 분해로 밝혀진 것:

스킬 4개 합계 데미지가 평타의 21.5배였다(최상위 티어 하나가 5타격 × 10대상 = 12배). 특정 레벨 구간에서 DPS가 22.5배 뛰고, 그 상태에서는 몬스터가 얼마나 강해지든 저항이 사실상 0이다. 시간의 대부분이 "전투"가 아니라 "레벨업 대기" 가 되어, 곡선을 만져도 페이스가 안 움직인다.

즉 파워 인플레가 남아 있으면 어떤 곡선 노브도 듣지 않는다. 수렴 순서를 이렇게 고정했다.

  1. 파워 인플레 차단 (스킬 계수 정상화, 골드 구매 비용에 구간 계단 도입)
  2. 그 다음에야 요구경험치가 전역 게인으로 작동한다
  3. 마지막에 구간별 미세 조정

| 조정 단계 | 19대 클리어 실측 | 목표 대비 | |---|---|---| | 착수 시점 | 7.2일 | ×0.02 | | 스킬 계수 정상화 + 몬스터 곡선 상향 | 11.8일 | ×0.03 | | + 구매 비용 구간 계단 | 13.0일 | ×0.03 | | + 요구경험치 전역 게인 | 75.3일 | ×0.18 |

앞의 두 단계는 배수를 거의 못 움직였지만, 그 두 단계가 없으면 네 번째 단계가 듣지 않는다. 이것이 이 프로젝트에서 얻은 가장 값비싼 교훈이다.

7.4 상충하는 축을 다루기

목표는 시간 축과 환생 축 두 개다. 그런데 요구경험치를 올려 시간을 늘리면 환생 횟수가 줄어든다 — 두 목표가 같은 노브에 반대 방향으로 매달려 있다. 전역 게인 하나로는 해결이 안 되고, 레벨 구간별 게인으로 분리해야 두 축을 동시에 맞출 수 있다.

이런 상충은 "곡선이 서로 물려 있다"는 이 도메인의 본질적 성질이고, 그래서 수렴 순서와 목적 함수를 문서로 고정해 두지 않으면 매번 처음부터 다시 헤매게 된다.

7.5 계측 도구를 함께 만들었다

목적 함수만 보면 "느리다/빠르다"만 알 수 있고 왜를 모른다. 그래서 진단 도구를 별도로 뒀다.

  • 정체 원인을 사망 / 시간 초과 / 처치 불가로 분리 계측
  • 레벨 격자 스냅샷 (도달 스테이지 · 골드 수입 · 구매 가능 스탯 수)
  • 파워 대비 몬스터 강도 분해 (평타 / 스킬 / 클리어 가능 스테이지)
  • 스탯 구매 1회의 전투력 기여 실측
  • 곱연산 옵션이 실제로 소비되는지 결과값 차이로 확인

마지막 항목은 "데이터에는 있는데 코드가 안 읽는" 유형의 조용한 실패를 잡기 위한 것이다.

7.6 재현성 확보

리포트용 측정은 고정 시드 난수를 따로 쓴다. 메인 난수를 소비하면 리포트를 켜고 끄는 것만으로 페이스가 달라지는 재현성 붕괴가 생긴다. 실제로 겪은 뒤 분리했다.

시뮬레이션의 한계도 명시해 두었다 — 칭호·던전·레이드·신념·광고는 꺼져 있고, 장비 옵션은 랜덤 리롤이라 실제 편차가 크다. "근사임을 아는 근사" 로 다루는 것이 중요했다.

8. 트러블슈팅

여기 모은 사례의 공통점은 엔진이 오류를 내지 않는다는 것이다. 크래시하는 버그는 알아서 드러나지만, 조용히 틀린 결과는 "정상 동작"으로 보인다.

8.1 조회 화면이 세이브를 덮어썼다

캡처 하네스는 실제 게임을 구동한다. 상점 화면을 픽스처로 캡처했는데, 구매를 하지 않았음에도 진행 중이던 캐릭터가 초기 픽스처로 덮였다.

원인은 조회 경로 안에 숨은 저장이었다. 화면 갱신이 "주기 초기화" 판정을 호출했고, 신규 픽스처의 초기화 인덱스가 미설정값이라 "주기가 바뀌었다"고 판단해 픽스처를 저장한 것이다.

더 나쁜 재발이 이어졌다. 앱 쉘 전체를 굴리는 하네스는 픽스처 주입만으로 막을 수 없었다. 프레임 루프를 도는 순간 오토세이브(칭호 판정 · 레벨업 · 스테이지 클리어)가 살아나고, 그 저장소는 합성 루트에서 이미 주입돼 있어 나중에 필드를 바꿔 끼워도 소용이 없었다.

  • 교훈 1: "읽기 전용 화면"이라는 판단은 호출 그래프 전체를 봐야만 할 수 있다.
  • 교훈 2: DI의 조립 시점이 곧 되돌릴 수 없는 시점이다.
  • 조치: 캡처 시작 시 저장 파일을 떠 두고 종료 직전 되돌리는 가드 모듈을 만들어, 앱 쉘을 띄우는 모든 하네스에 배선했다. 프로세스가 중간에 죽으면 되돌리지 못하므로 "실행 전 백업"은 여전히 원칙으로 남겼다.

8.2 세로 게임이 가로로 빌드됐다

프로젝트 설정에 화면 방향이 문자열로 들어 있었다. 구버전 문법이다. 현재 엔진에서 이 설정은 정수 enum이고, 엔진은 오류 대신 문자열을 정수로 변환해 0 = 가로로 읽었다. Android 익스포터가 그 값을 그대로 매니페스트에 구워서, 파일에는 세로라고 적혀 있는데 APK는 가로로 나갔다.

  • 교훈: 설정 파일은 값을 읽는 것만으로는 검증이 안 된다. 타입까지 단정해야 한다.
  • 조치: 표시 설정의 값과 타입을 함께 검사하는 검증 스크립트를 추가했다.

8.3 파싱 에러가 "메서드 없음"으로 위장했다

씬은 붙은 스크립트가 파싱에 실패해도 스크립트 없이 그대로 로드된다. 그래서 증상이 파싱 에러가 아니라 런타임의 "존재하지 않는 함수" 오류로 나타나고, 원인을 엉뚱한 곳에서 찾게 된다.

실제 사례는 서로 다른 enum을 같은 함수 인자로 넘긴 것이었다. 같은 값 체계라도 enum 타입이 다르면 언어가 공유를 거부한다 — 서수 기반 헬퍼로 우회했다.

더 심각한 건 발견 시점이었다. 검증 스크립트도, 렌더 캡처도, 클래스 캐시 재생성도 전부 놓쳤고, APK 빌드가 처음으로 잡았다(익스포트는 전 스크립트를 싣는다). 그 화면은 4주간 깨진 채로 있었다.

  • 조치: 전 스크립트(약 294개)를 문법 검사만 수행하는 도구를 만들었다. 1분이면 끝난다. 빌드까지 가지 않고 같은 그물을 칠 수 있다.

8.4 체력 곡선의 단조성이 무너져 있었다

몬스터 체력은 대스테이지 내부 배수가 누적된 뒤 경계에서 리셋되는 구조다. 따라서 다음 조건을 만족해야 한다.

경계 배수 ≥ 내부 배수 ^ (대스테이지당 단수 − 2)

이걸 어기면 다음 월드의 첫 단계가 직전 단계보다 약해진다. 실측 결과 이전 곡선은 15개 경계 중 14개에서 체력이 감소했고(최대 170배), 아무도 알아채지 못한 채 그 위에서 캘리브레이션이 진행되고 있었다.

  • 교훈: 곡선은 값이 아니라 조건식으로 검증해야 한다. 표를 눈으로 봐서는 안 보인다.

8.5 시뮬레이터가 "그럴듯하게" 틀렸다

시뮬 로드아웃에 존재하지 않는 스킬 ID를 쓰면, 조회가 빈 값을 반환하고 조용히 스킵된다. 크래시가 나지 않으므로 시뮬은 정상 완주하고, 결과는 스킬 DPS 0 + 스킬 포인트 전량 낭비 상태의 페이스다. 그럴듯해 보여서 그 값이 문서에 기록된 적이 있다.

  • 교훈: 실패가 예외로 드러나지 않는 조회 API는, 호출 측이 실존을 단정해야 한다.

8.6 렌더 캡처의 함정 두 가지

(a) 한 프로세스에서 두 번째 캡처가 이전 프레임을 돌려준다. 상태를 바꿔가며 여러 장을 찍었더니 첫 장만 정상이고 나머지는 직전 상태 그대로였다. 프레임 대기를 8→60으로 늘려도, 화면 전체를 새빨갛게 칠해도 반영되지 않았다. 라벨 텍스트 하나만 바꾸는 최소 재현에서도 동일했다. (항상 재현되지는 않는다 — 일부 하네스는 한 프로세스에서 여러 장을 정상적으로 찍는다. 개발 환경 조합 한정일 가능성이 있고 원인은 특정하지 못했다.)

확실히 동작하는 유일한 패턴은 상태 1개당 프로세스 1개, 한 장만 찍고 즉시 종료다. 즉 "언제나 성공하는 첫 캡처"만 반복하는 것이다.

가장 위험한 건 시각적으로 그럴듯해 보인다는 점이다. 그래서 새 하네스를 만들 때는 두 번째 이후 이미지가 이전과 바이트 단위로 동일한지 확인하는 절차를 규약에 넣었다.

(b) 순간 연출은 통합 캡처로 찍을 수 없다. 메인 화면 하네스는 전투를 한 프레임 안에서 압축 진행하므로 트윈이 0.22초만 흐른다. 0.17초에 소멸하는 평타 이펙트가 정확히 그 공백에 걸려 "이펙트가 안 나온다"로 30분을 썼다. → 발사 시각을 직접 정하는 전용 하네스로 분리했다.

그 하네스는 픽셀 비교를 위해 고정 FPS와 파티클 시드 고정까지 강제한다 (고정하지 않으면 같은 코드로 두 번 찍어도 1,500px 넘게 달라진다). 또 세로 기준 캔버스가 가로로 납작한 캡처 창에서 3배 이상 늘어나는 문제가 있어, 전용 하네스는 콘텐츠 스케일을 끄고 찍는다 — 그러지 않으면 실기와 크기 비교가 성립하지 않는다.

8.7 스프라이트·에셋 전처리 파이프라인

원화를 게임 에셋으로 굽는 과정도 만만치 않았다. 21종의 Python 도구가 여기서 나왔다.

  • 회전·리샘플은 알파 프리멀티플 이후에 해야 한다. 투명 픽셀의 RGB에 원본 배경색이 구워져 있어서, 먼저 회전하면 배경색이 외곽으로 번진다.
  • 색상 키잉은 알파가 이진이라 흰 테두리를 남긴다. 최외곽 한 겹의 알파를 되살리는 후처리가 필요하고, 이때 배경색은 가공본이 아니라 원본에서 읽어야 한다.
  • "투명 배경 PNG"에 체커보드가 구워져 있을 수 있다. 내비게이션 아이콘 5장 전부 반투명 외곽 픽셀의 RGB가 편집기 체커보드였다(2.4~6.1%). 어두운 배경에서는 글로우처럼 보여 드러나지 않다가, 밝은 배경으로 바꾸자 회색 얼룩이 됐다. → 알파를 유지한 채 RGB만 복원하는 도구를 만들었다.
  • 검흔 텍스처는 주축각을 구해 수평으로 정렬한 뒤 굽는다 — 셰이더가 가로축을 진행축으로 쓰기 때문이다.
  • 같은 구성의 시트라도 종족별로 좌표가 다르다(실루엣 IoU 0.43). 탐색 창을 따로 뒀다.
  • 낱장 프레임에 칸 테두리선과 프레임 번호 글자가 구워져 오는 경우가 있어, 선 제거(또렷한 선 + 흐릿한 잔선 2단계)와 모서리 제외를 파이프라인 단계로 넣었다.
  • 스프라이트 정렬은 눈으로 보면 놓친다. 대기 모션과 걷기 모션의 픽셀 스케일이 같은지를 알파 행 밀도로 실측해 2% 이내로 강제한다 (경계 상자는 무기가 뻗은 방향에 따라 프레임마다 달라져 쓸 수 없다).

8.8 UI 레이아웃에서 반복된 함정

| 함정 | 실제 증상 | 해결 | |---|---|---| | z_index가 트리 순서를 이김 | 모달 위로 스테이지 카드·몬스터 HP바가 떠오름 | 무엇 위에든 떠야 하는 것은 오버레이 전용 z 상수 | | 플로팅 위젯이 입력을 삼킴 | 카드 배경이 모달 닫기 버튼을 가로챔 | 버튼이 아닌 Control은 입력 통과 처리 | | 컨테이너 자식의 오프셋 무효 | 전투 캔버스를 넓히려 했으나 아무 효과 없음 | 부모를 컨테이너가 아닌 Control로 | | 스타일의 내부 여백이 최소 크기에 가산 | 진행바를 얇게 만들 수 없음(48px 바닥) | 여백·모서리 반경을 함께 조정 | | 손으로 만드는 레코드에 필드 누락 | 화면 즉사, 실행 전에는 안 잡힘 | 생성 경로를 하나로 통합 (읽는 쪽 기본값 방어는 다음 누락을 숨기므로 금지) | | 캐시된 뷰를 해제 후 재사용 | 해제한 노드를 다시 붙이면 크래시 | 캐시된 노드는 해제하지 않고 떼어내기만 | | 컨테이너 안 비율 유지 이미지 | 높이가 0으로 접히거나 패널 밖으로 넘침 | 크기 확정 시점(리사이즈 신호)에 높이를 직접 지정 |

8.9 이중 지급을 막는 구조적 규칙

던전 전투 세션은 일반 처치 보상 유스케이스를 호출하지 않는다. 호출하면 처치 보상과 던전 정산 보상이 이중 지급된다. 같은 이유로 소탕(전투 생략)은 클리어 정산과 같은 지급 함수를 공유한다 — 보상 규칙을 두 번 적으면 한쪽만 고쳤을 때 갈라지기 때문이다.

이런 규칙은 주석으로 남겨도 잊힌다. 그래서 호출 관계 자체를 그렇게만 가능하도록 배치했다.

8.10 조립 순서가 만든 조용한 기본값

합성 루트에서 리소스 로드 순서가 잘못되면, 뒤에 로드되는 쪽이 예외 없이 조용히 기본값으로 떨어진다. 시작 스탯과 레벨업 증가량을 소유하는 데이터는 그것을 소비하는 유스케이스보다 먼저 로드돼야 한다. 같은 함정을 두 블록에서 겪은 뒤, 순서 의존을 조립부 최상단에 명시했다.

같은 계열로 enum을 데이터가 정수로 저장한다는 점도 있다. enum 멤버를 지우면 뒤 값이 한 칸씩 밀리는데 아무 오류도 나지 않는다 — "로드된 값이 의도한 상수와 같은가"를 단정하는 검증을 통과시키는 것을 규칙으로 삼았다.

9. 회고 — 설계 원칙으로 남은 것

이 프로젝트가 증명한 것

  1. 아키텍처는 목적이 아니라 능력이다. 레이어를 나눈 진짜 대가는 "깔끔함"이 아니라 400일 분량의 플레이를 몇 분 만에 돌릴 수 있는 능력이었다. 도메인이 씬 트리를 참조하는 순간 이 능력은 전부 사라진다.

  2. 크래시하지 않는 버그가 가장 비싸다. 이 프로젝트에서 가장 오래 살아남은 문제들은 전부 오류를 내지 않았다 — 4주간 깨진 화면, 14개 경계에서 뒤집힌 곡선, 가로로 빌드된 세로 게임, 그럴듯하게 틀린 시뮬 결과. 그래서 검증의 초점을 "예외가 나는가"에서 "조용히 다른가" 로 옮겼다.

  3. 공식을 두 곳에 적으면 반드시 갈라진다. 두 번 겪고 나서 규칙으로 굳혔다: 곡선마다 유일한 소유자를 정하고, 그 일치를 사람이 아니라 스크립트가 강제한다.

  4. 방어 코드가 항상 옳은 것은 아니다. 누락된 필드에 기본값을 채워 넣는 방어는 다음 누락을 숨긴다. 실패해야 할 곳에서 실패하게 두고, 대신 생성 경로를 하나로 모으는 쪽을 택했다.

  5. 1인 개발에서 문서는 오버헤드가 아니라 인프라다. "왜 그렇게 했는가"와 "무엇을 밟았는가"를 남기지 않으면 6주 전의 결정을 재검토하느라 시간을 쓰고, 이미 폐기한 접근을 다시 시도하게 된다. 실제로 "다시 시도하지 말 것" 목록을 따로 유지한다.

다시 한다면 다르게 할 것

  • 캘리브레이션은 콘텐츠보다 먼저 최소 골격을 잡았어야 했다. 성장 축을 8개까지 늘린 뒤에 곡선을 맞추려니, 축 하나를 건드리면 나머지 일곱이 함께 움직였다. 축이 2~3개일 때 목표 페이스와 수렴 순서를 먼저 확정했다면 재작업이 훨씬 적었을 것이다.
  • 전투 모델의 근본 가정(동시 교전 수)을 시뮬에 더 일찍 반영했어야 했다. 1마리 모델로 돌린 기간의 계측치는 전부 폐기됐다.
  • 검증 도구의 "거짓 통과"를 처음부터 의심했어야 했다. 블록 완주 기록, 이미지 바이트 비교, 로드아웃 실존 검증은 전부 사고를 겪은 뒤에 추가됐다.
