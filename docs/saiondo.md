## 1. 무엇을 만들었고, 왜 어려웠나

### 문제

연락처 앱에는 사람이 있지만 **관계**가 없다. 몇 년 동안 연락하지 않은 사람과 매주 만나는 사람이 같은 목록에 나란히 있다. 그래서 소중한 사람을 놓친다.

이 앱은 사용자가 고른 사람들에 대해 만남·연락·선물·경조사 같은 교류를 기록하고, "지금 이 관계가 어떤 상태인가"를 한 숫자로 보여준다.

### 진짜 어려운 지점은 기술이 아니었다

CRUD와 화면은 어렵지 않다. 어려운 것은 두 가지였다.

**첫째, 사람 사이의 관계를 숫자로 바꾸는 규칙을 정하는 일.**
아무 규칙이나 정하면 숫자가 관계를 설명하지 못한다. 실제로 첫 구현이 그랬고, 모델을 다시 세워야 했다. (→ 2장)

**둘째, 이 앱이 다루는 데이터가 하필 가장 민감한 종류라는 것.**
이름, 전화번호, 누구를 언제 만났는지, 경조사에 얼마를 냈는지. 유출되면 곤란한 정도가 아니라 사람 관계를 망가뜨린다. 그래서 "안전하게 만들자"가 아니라 **"안전하지 않은 코드를 쓸 수 없게 만들자"** 로 접근했다. (→ 3장, 6장)

### 제품 원칙 — 죄책감을 주지 않는다

관계를 수치화하는 앱은 쉽게 사람을 평가하는 도구가 된다. 그래서 문구 수준까지 원칙을 정했다.

| 쓰지 않는 표현 | 쓰는 표현 |
| --- | --- |
| "관리를 못하고 있어요" | "오랫동안 만나지 않았어요" |
| "관계가 나빠졌습니다" | "오늘 연락해보는 건 어때요?" |

이 원칙은 코드에도 반영되어 있다. 미교류 알림은 **기본값이 꺼짐**이다. 도움이 되는 사람도 있지만 "연락 안 했다"는 지적으로 읽힐 수 있어서, 사용자가 직접 켜게 했다.

## 2. 관계 온도 — 가장 오래 고민한 것

### 시작점

사람의 체온에서 따와 **새 관계는 36도**에서 시작한다. 교류하면 오르고, 한 달 동안 아무 교류가 없으면 그 달 끝에 1도 내려간다. 범위는 0~100.

교류 종류별 가중치는 "얼마나 드문 일인가"로 정했다.

| 교류 | 가중치 |
| --- | ---: |
| 연락 | +1 |
| 전화 | +2 |
| 만남 | +3 |
| 생일 축하 | +4 |
| 경조사비 | +8 |
| 생일 선물 | +10 |
| 경조사 참석 | +15 |

경조사에 함께 있어 준 한 번은 가벼운 연락 여러 번보다 큰 일이다. 순서 자체가 의미를 담고 있어서, 값을 조정할 때도 이 순서를 깨지 않는다는 규칙을 코드 주석에 남겼다.

경조사비는 **금액과 무관하게 항상 같은 값**이다. 돈을 많이 쓸수록 가까운 관계라고 보지 않는다.

### 발견한 문제 — 모두가 100에 붙는다

초기 구현은 가중치를 그대로 더했다. 만남이 +5였다.

```text
36 + (5 × 10회) = 86
```

**열 번만 만나면 86도.** 한 달에 두 번 만나는 평범한 사이가 1년이면 천장에 닿는다. 그러면 온도가 관계를 구분하지 못한다. 10년 동안 매주 만난 사람과 1년 동안 한 달에 두 번 만난 사람이 **똑같이 100**이 된다.

가중치를 낮추는 것으로는 해결되지 않는다. 도달 시점만 뒤로 미뤄질 뿐 결국 모두 100에 모인다. 이건 파라미터 문제가 아니라 **모델의 문제**였다.

### 해결 — 남은 여백에 비례해 오르게 한다

선형 누적을 버리고, 남은 여백에 비례하는 방식으로 바꿨다.

```text
실제 상승 = 가중치 × (100 − 현재 온도) / (100 − 36)
```

기준점을 시작 온도인 36으로 잡은 것이 핵심이다. 그래야 위 표의 가중치가 **"새로 만난 사람에게 한 번 했을 때 오르는 값"** 이라는 자연스러운 의미를 갖는다.

| 현재 온도 | 만남(+3)이 실제로 올리는 값 |
| --- | --- |
| 36 | 3.0 |
| 60 | 1.9 |
| 80 | 0.9 |
| 95 | 0.2 |

36 아래에서는 비율이 1을 넘는데, 여기서는 1로 자른다. 멀어진 관계가 한 번의 교류로 훌쩍 오르는 것도 관계를 잘못 설명하기 때문이다.

### 결과 — 숫자가 관계를 설명하기 시작했다

| 상황 | 온도 |
| --- | --- |
| 만남 10회 | 60 |
| 두 달에 한 번 만남 (1년) | 46 |
| 한 달에 한 번 만남 (1년) | 64 |
| 한 달에 두 번 만남 (1년) | 80 |
| 주 1회 만남 (1년) | 95 |
| 한 달에 두 번 만남 (3년) | 98 |

100은 사실상 닿지 않는 값이 됐다. 그리고 월간 비활동 감소(-1)는 **온도와 무관하게 그대로 빠지기 때문에**, 높은 온도를 유지하려면 실제로 계속 이어져야 한다. "꾸준히 자주"를 값으로 표현하는 방식이다.

### 이 결정이 데이터 접근 방식까지 바꿨다

여기서 파생된 설계 이슈가 하나 있었고, 개인적으로 가장 흥미로웠던 부분이다.

**교류 하나를 반영할 때마다 0~100으로 자른다.** 전부 더한 뒤 마지막에 한 번 자르지 않는다. 값이 달라지기 때문이다.

그런데 이렇게 하면 **"만남 12회, 연락 30회" 같은 종류별 합계만으로는 온도를 계산할 수 없다.** 100에 도달한 뒤의 교류는 버려지므로, 시간 순서대로 하나씩 반영해야만 한다.

그래서 교류 저장소가 두 가지 조회를 따로 제공하게 했다.

| 용도 | 조회 형태 | 이유 |
| --- | --- | --- |
| 상세 화면 표시 | 종류별 집계 카운트 | "만남 4회 / 연락 3회"를 보여주기만 하면 된다 |
| 온도 계산 | 종류 + 날짜만, 시간순 스트림 | 순서대로 반영해야 하므로 이벤트가 필요하다 |

온도 계산용 조회는 **컬럼 3개만** 가져오고, 화면에 보이는 사람의 것만 조회한다. 전체 교류를 메모리에 올리지 않는다. 도메인 규칙 하나가 저장소 인터페이스의 모양을 결정한 사례다.

### 결정성 (determinism)

온도 계산은 현재 시각을 절대 읽지 않는다. 기준일을 인자로 받는다.

```text
계산({ 초기온도, 관계시작일, 교류이벤트목록, 기준일 })
```

덕분에 테스트가 시간에 의존하지 않고, "3년 뒤 이 관계는 몇 도인가" 같은 검증을 그냥 쓸 수 있다. 그리고 이 규칙은 **ESLint로 강제**된다. 도메인 계층에서 현재 시각을 읽으면 린트가 막는다. (→ 3장)

비활동 감소를 세는 달의 범위도 명확히 정의했다. **등록한 다음 달부터 기준일 전 달까지.** 등록한 달과 진행 중인 달은 "한 달 전체"가 아니므로 세지 않는다. 이런 경계 조건이 흔들리면 같은 데이터에서 다른 온도가 나온다.

## 3. 아키텍처 — 규칙을 문서가 아니라 도구로 강제하기

### 계층

```text
화면 → 서비스 → Repository 인터페이스 → 로컬(SQLite) / 클라우드
                        ↑
                    도메인 (순수 계산)
```

흔한 계층 구조다. 흔하지 않은 부분은 **이 규칙을 어길 수 없게 만든 방법**이다.

### 린트 규칙으로 아키텍처를 지킨다

문서에 "도메인은 UI에 의존하지 않는다"라고 적어두면 지켜지지 않는다. 바쁠 때 한 줄 import 하면 그만이고, 리뷰에서 놓치면 그대로 남는다. 그래서 규칙으로 만들었다.

| 규칙 | 막는 것 | 이유 |
| --- | --- | --- |
| 도메인 계층의 import 제한 | `react` · `react-native` · `expo*` · UI 계층 · 데이터 계층 | 도메인을 순수하게 유지한다 |
| 도메인 계층의 현재 시각 읽기 금지 | 인자 없는 `new Date()`, 현재 타임스탬프 조회 | 계산을 결정적으로 만든다 |
| 콘솔 직접 호출 전면 금지 | `console.*` | 개인정보가 로그로 새는 경로를 원천 차단한다 |

세 번째가 특히 중요하다. 이 앱의 로그에 이름이나 전화번호가 찍히면 그 자체로 사고다. 그래서 로깅 창구를 하나로 고정하고 다른 경로를 아예 막았다. 개발용 스크립트와 서버 함수처럼 앱 번들에 들어가지 않는 코드에만 예외를 뒀다.

**"조심하자"를 "못 하게 하자"로 바꾼 것**이 이 프로젝트에서 만족스러운 결정 중 하나다.

### 로컬 우선 (Local-first)

무료 요금제는 **로컬 전용**으로 동작한다. 네트워크 없이 모든 핵심 기능이 돌아간다.

이게 단순히 "오프라인 지원"이 아닌 이유는, 이 선택이 아키텍처 전체를 결정했기 때문이다.

- 화면은 저장소를 직접 알지 못한다. Repository 인터페이스만 본다.
- 그래서 나중에 "로컬 + 클라우드 동기화" 구현으로 갈아 끼워도 화면은 그대로다.
- 로컬 DB 초기화가 실패해도 앱은 열린다. 루트 레이아웃이 오류 화면과 재시도를 보여준다.

### 마이그레이션

로컬 SQLite는 버전 번호 기반으로 마이그레이션을 순서대로 적용한다. 각 버전은 하나의 트랜잭션이다.

두 가지 규칙을 세웠다.

1. **이미 배포된 마이그레이션은 절대 수정하지 않는다.** 항상 새 버전을 덧붙인다.
2. **DB 버전이 앱이 아는 버전보다 높으면 실행을 멈춘다.** 사용자가 구버전 앱으로 되돌아간 경우다. 그냥 진행하면 앱이 모르는 스키마를 건드려 데이터가 깨진다. 멈추고 업데이트를 안내하는 게 맞다.

### 네이티브 모듈은 Jest에서 못 돈다 → 별도 검증 스크립트

SQLite는 네이티브 모듈이라 Jest에서 실행할 수 없다. 그렇다고 스키마를 검증 없이 둘 수는 없었다.

그래서 **마이그레이션 SQL을 Node 내장 SQLite 엔진에 실제로 적용해보는 스크립트**를 따로 만들었다. 문법 오류뿐 아니라 제약조건이 의도대로 거부하는지까지 확인한다. (기기의 SQLite와 버전이 다를 수 있다는 한계는 문서에 명시해뒀다.)

## 4. 데이터 모델 — 카운터를 저장하지 않는다

### 원본은 이벤트다

```text
저장하지 않는 것:  만남횟수 = 12,  선물횟수 = 3
저장하는 것:       { 만남, 2026-03-14 }, { 만남, 2026-04-02 }, ...
```

카운터를 원본으로 두면 편하다. 조회가 빠르고 코드가 짧다. 하지만 교류를 수정하거나 삭제하는 순간 카운터가 조용히 어긋나고, **되돌릴 근거가 사라진다.** 어떤 값이 맞는지 확인할 방법이 없어진다.

이벤트를 원본으로 두면 통계는 언제든 다시 계산할 수 있고, 나중에 "작년 3분기에 누구를 제일 많이 만났나" 같은 질문이 생겨도 데이터가 이미 거기 있다. 실제로 통계 탭과 심층 분석 기능을 나중에 추가할 때 **스키마를 전혀 건드리지 않았다.**

캐시 카운터를 도입한다면 언제 갱신되고 언제 무효화되는지를 명확히 관리한다는 조건을 붙여뒀다. 지금은 필요하지 않아 넣지 않았다.

### 무결성은 DB가 지킨다

애플리케이션 검증은 사용자에게 친절한 메시지를 주기 위한 것이고, **진짜 방어선은 스키마**다. 앱 코드는 언젠가 버그가 생기지만 제약조건은 그렇지 않다.

- 이름 빈 문자열 금지, 온도 범위 제한
- 생월·생일은 둘 다 있거나 둘 다 없어야 함 (한쪽만 있는 생일은 의미가 없다)
- 교류 종류는 정해진 7가지만, 날짜는 정해진 형식만
- 금액/방향 필드는 경조사비 교류에만 존재 (다른 종류에는 NULL이어야 함)
- 관계 삭제 시 교류·약속 CASCADE 삭제
- 하나의 교류를 두 약속에 연결 불가 → **완료 약속의 만남 중복 집계를 DB가 막는다**
- 같은 기기 연락처의 중복 등록 불가 (부분 유니크 인덱스)

마지막 두 개가 특히 마음에 드는 부분이다. 애플리케이션 로직으로도 막지만, 경합이나 버그로 뚫려도 DB가 최종적으로 거부한다. **두 겹으로 막는다.**

### 약속과 만남을 자동으로 잇지 않는 이유

완료된 약속을 만남 교류로 **자동 전환하지 않는다.**

약속을 잡아두고 실제로는 못 만났을 수도 있고, 이미 따로 기록했을 수도 있다. 자동으로 만들면 사용자가 기록하지 않은 만남이 데이터에 생기고, 그게 온도에 반영된다. 관계를 설명하는 숫자에 사실이 아닌 게 섞이는 셈이다.

그래서 완료 처리할 때 **"만남으로도 기록할까요?"** 를 묻고, 사용자가 고른 경우에만 만든다. 그리고 교류를 만든 뒤 약속 갱신에 실패하면 **만든 교류를 되돌린다.** 주인 없는 기록을 남기지 않기 위해서다.

## 5. 보안과 신뢰 경계

### 세 가지 신뢰 수준을 구분했다

결제가 걸린 기능에서 "무엇을 어디까지 믿을 것인가"를 명시적으로 나눴다.

| 판단 | 근거 | 위조 가능성 | 대응 |
| --- | --- | --- | --- |
| 화면에 보이는 요금제 | 결제 SDK | 낮음 | 그대로 사용 |
| 오프라인에서의 인원 제한 | 기기 로컬 캐시 | **있음** | **의도적으로 허용** |
| 클라우드 백업 허용 | 서버 권한 테이블 + RLS | 없음 | 서버가 다시 판단 |

두 번째 줄이 이 설계의 핵심이다.

기기 캐시를 조작하면 친구 수 제한을 우회할 수 있다. 막을 수 있지만, 막으려면 매번 서버에 물어야 하고 그러면 **무료 요금제의 오프라인 동작이 깨진다.** 그건 제품의 근간이다.

그래서 이렇게 판단했다. 캐시를 고쳐서 얻는 것은 **자기 기기의 저장 공간**뿐이다. 서버 자원도, 남의 데이터도 아니다. 그 정도 위험 때문에 오프라인 동작을 포기하지 않는다. 대신 **서버 자원을 쓰는 기능(클라우드 백업)은 서버가 반드시 다시 판단한다.**

### 서버는 클라이언트가 보낸 값을 믿지 않는다

두 겹이다.

**① 소유권은 계정이지 기기가 아니다.**

초기에 기기 식별자를 소유자로 쓰는 안을 검토했다가 버렸다. 이유는 세 가지.

- 기기 식별자는 클라이언트가 보내는 값이라 위조할 수 있고, RLS로 막을 수 없다.
- 기기를 잃으면 데이터도 잃는다. **백업의 목적과 정반대다.**
- 두 플랫폼 모두 안정적인 기기 식별자를 주지 않고, 개인정보 고지 대상이 된다.

지금은 인증 토큰의 실제 소유자와 대조한다. 앱이 사용자 id를 보내지만 서버가 토큰의 주인과 맞는지 확인한 뒤에만 통과시킨다. 기기 식별자는 "어느 기기에서 올렸는지" 기록용으로만 쓰고, 하드웨어 식별자를 읽지 않는 앱 자체 생성 UUID다.

**② 결제 웹훅의 본문을 믿지 않는다.**

웹훅이 "이 사용자는 상위 요금제"라고 보내와도 그 값을 쓰지 않는다. **결제 사업자 API에서 다시 읽는다.** 요청은 "이 사용자를 다시 확인해봐"라는 신호일 뿐이다. 그래서 엔드포인트 주소를 알아낸 사람이 임의의 본문을 보내도 권한이 바뀌지 않는다.

웹훅은 결제 사업자가 부르므로 자체 인증 토큰이 없다. 그래서 플랫폼의 기본 토큰 검증을 끄는 대신, **인증을 함수 안으로 옮겼다.** 웹훅 경로는 비밀값을 상수 시간으로 대조하고, 앱 경로는 토큰의 주인을 인증 서비스에 물어 확인한다. 인증이 사라진 게 아니라 위치가 바뀐 것이다.

### 비밀 키가 앱에 들어가는 것을 코드가 거부한다

모바일 앱 번들은 뜯어볼 수 있다. 여기 들어간 키는 공개된 것과 같다.

환경 변수를 읽는 지점을 한 곳으로 고정하고, 그 자리에서 **검증을 걸었다.**

- 서버 전용 비밀 키 형태가 들어오면 **즉시 실패**시킨다.
- 결제 SDK 키가 공개 키 형식인지 접두사로 확인한다. 비밀 키와 생김새가 비슷해서 실수로 넣기 쉬운 값이다.

서버에서만 쓰는 비밀값은 `.env`가 아니라 서버 측 시크릿으로만 등록한다. 실수로 앱에 들어갈 경로 자체를 없앴다.

### 강등돼도 자기 데이터는 지킨다

구독이 끝나면 **새 백업을 올리는 것만** 막는다. 이미 올려둔 백업의 조회·복구·삭제는 그대로 열어둔다.

돈을 내지 않으면 자기 데이터를 되찾을 수 없게 만드는 건, 기술적으로 가능해도 해서는 안 되는 일이라고 판단했다. 일회성으로 구매한 인원 추가분도 구독 강등과 무관하게 유지된다.

### 백업 복원 시 복원하지 않는 것

백업 파일은 사용자가 편집할 수 있는 JSON이다. 그래서 복원할 때 **기기 식별자와 요금제 권한은 복원하지 않는다.**

- 기기 식별자를 복원하면 여러 기기가 같은 id를 갖게 된다.
- 요금제 권한을 복원하면 **파일을 고쳐서 유료 기능을 열 수 있다.**

파일 가져오기와 클라우드 복구가 같은 복원 경로를 공유하게 만들어서, 이 규칙이 양쪽에 자동으로 적용되도록 했다.

## 6. 개인정보를 기본값으로 보호하기

이 앱이 다루는 데이터의 성격상, 개인정보 보호를 최우선 우선순위로 두고 시작했다.

### 절대 하지 않는 것

- 주소록 전체를 자동 업로드
- 모든 연락처를 자동으로 친구 등록
- 연락처 내용을 로그에 출력
- 분석 이벤트에 이름/전화번호 포함
- 비밀 키 커밋

### 연락처 접근 설계

| 원칙 | 구현 |
| --- | --- |
| 필요한 순간에만 묻는다 | 앱 시작 시 권한을 요청하지 않는다. 연락처를 쓰려는 순간에만 |
| 최소한만 읽는다 | 이름 / 전화번호 / 생일 세 필드만 요청한다 |
| 읽은 것을 저장하지 않는다 | 조회 결과는 화면에만 있고, **사용자가 고른 사람만** 관계가 된다 |
| 거부해도 막다른 길이 없다 | 권한 없이도 앱 전체를 쓸 수 있다. 직접 추가로 이어진다 |
| 주소록 데이터를 신뢰하지 않는다 | 생일 형식이 이상하면 **생일만 버리고 사람은 살린다** |

마지막 항목은 사소해 보이지만 실제로 중요했다. 주소록에는 별별 형식의 날짜가 들어 있어서, 하나라도 파싱에 실패하면 가져오기 전체가 실패하는 구조는 쓸 수 없었다.

### 알림 본문에서 이름을 뺀 경우

로컬 알림은 잠금화면에 뜬다. 옆 사람이 볼 수 있다.

| 알림 | 본문에 담는 것 |
| --- | --- |
| 생일 | 이름 (축하가 목적이므로 이름이 필요하다) |
| 약속 | 장소 (이름은 제목에) |
| 미교류 | **인원수만.** 이름을 넣지 않는다 |

"○○님과 3개월째 연락하지 않았어요"가 잠금화면에 뜨는 상황을 만들고 싶지 않았다. 그래서 이 알림만 이름 없이 "챙겨볼 관계가 N명 있어요" 형태로 보낸다.

### 알림은 전부 로컬이다

서버도 푸시 토큰도 쓰지 않는다. 무료 요금제가 오프라인으로 동작해야 하므로 이 방식이 맞고, 부수적으로 **"누구의 생일이 언제인가"가 서버로 나가지 않는다.**

### 데이터 내보내기 파일 취급

내보내기 파일에는 이름·전화번호·메모가 그대로 들어간다. 그래서:

- 파일은 **캐시 폴더에만** 만든다.
- 어디에 저장할지는 사용자가 공유 시트에서 정한다.
- 앱이 임의로 다른 곳에 복사본을 남기지 않는다.

### 가져오기는 2단계 확인

파일을 고르는 순간 곧바로 덮어쓰지 않는다.

```text
1. 파일 선택 → 읽고 검증만 한다. 아직 아무것도 바꾸지 않는다.
2. 확인 창에 파일 안의 내용을 보여준다 — 친구 N명 / 교류 N건 / 약속 N건, 파일명
3. 확인을 받은 뒤에 덮어쓴다
```

잘못된 파일을 골랐을 때 되돌릴 방법이 없기 때문이다. 파일 안에 실제로 뭐가 들었는지를 보여주면 사용자가 바로 알아챌 수 있다.

## 7. 성능 — 어디까지 버티는지 알고 만들기

성능은 "빠르게 만들었다"보다 **"어디서 무너지는지 알고 있다"** 가 중요하다고 봤다.

### 온도 정렬의 한계를 알고 선을 그었다

관계 온도는 계산된 값이라 **SQL로 정렬할 수 없다.** 불러온 뒤에 정렬해야 한다.

그래서 친구 리스트는 한 번에 최대 500명까지만 읽도록 상한을 뒀다. 렌더링은 리스트 가상화가 처리하므로 무료 100명 / 중간 요금제 300명 기준으로는 문제가 없다.

그리고 **무제한 요금제를 열기 전에 이 방식을 다시 봐야 한다**는 것을 아키텍처 문서의 "아직 결정하지 않은 것"에 명시해뒀다. 알면서 남겨둔 부채와 모르고 있는 부채는 다르다.

### 조회를 용도별로 나눴다

앞서 언급한 대로, 온도 계산용 조회는 필요한 **컬럼 3개만** 가져오고 화면에 보이는 사람의 것만 조회한다. 표시용 집계와 계산용 이벤트 스트림을 하나의 조회로 합치지 않았다.

### 자동 백업의 불필요한 업로드를 막았다

자동 백업은 앱을 열고 닫을 때마다 동작한다. 바뀐 게 없는데도 매번 올리면 **사용자의 데이터 요금과 서버 비용을 그냥 태운다.** 스냅샷은 통째로 올리기 때문에 한 번에 수백 KB가 오간다.

그래서 올리기 전에 "지난번과 같은가"를 먼저 본다. **스냅샷을 만드는 것(로컬 읽기)은 싸고, 올리는 것(네트워크)이 비싸다**는 비대칭을 이용했다.

전체 내용을 해싱하지 않고, 각 목록의 **개수 + 가장 최근 수정 시각**으로 판단한다.

| 변경 | 감지 방법 |
| --- | --- |
| 수정 | 최근 수정 시각이 바뀐다 |
| 추가 / 삭제 | 개수가 바뀐다 |
| 하나 지우고 하나 넣기 | 개수는 같지만 새 항목의 수정 시각이 더 최근이다 |

여기서 함정이 하나 있었다. **설정값 중에는 백업을 하면 바뀌는 값이 있다** (마지막 백업 시각, 이 변경 감지 값 자체). 그대로 넣으면 백업할 때마다 값이 달라져서 "항상 바뀐 것"으로 보이고, 건너뛰기가 영원히 동작하지 않는다. 그런 키를 제외하고 계산하도록 했다.

### 알림 예약은 부분 갱신하지 않는다

친구를 추가하거나 약속을 바꿀 때마다 어떤 알림이 영향받는지 추적해서 부분 갱신하는 대신, **앱이 앞으로 올 때마다 전부 지우고 다시 잡는다.**

부분 갱신이 효율적이지만 어긋날 여지가 크다. 알림 수십 개 재예약은 충분히 싸고, 전체 재계산은 항상 정확하다. **정확성을 위해 약간의 낭비를 선택한 사례다.**

플랫폼 제약(iOS는 앱당 64개 대기 한도)에 맞춰 48개 / 60일 이내로 상한을 뒀다.

### 스플래시를 초기화와 병렬로 돌린다

스플래시 애니메이션과 로컬 DB 마이그레이션은 **동시에** 진행되고, 둘 다 끝나야 화면을 넘긴다. 애니메이션 때문에 앱이 느려지지 않고, 초기화가 빨라도 애니메이션이 잘리지 않는다.

"동작 줄이기(reduce motion)"를 켠 사용자에게는 애니메이션 없이 완성된 로고만 잠깐 보여준다.

## 8. 다국어 — 라이브러리 없이, 대신 타입으로

한국어·영어·일본어를 지원한다. **번역 라이브러리를 넣지 않았다.**

"단순한 편의를 위해 패키지를 추가하지 않는다"는 원칙에 따라, 먼저 라이브러리 없이 필요한 것을 다 할 수 있는지 확인했다. 결과적으로 할 수 있었고, 오히려 더 강한 보장을 얻었다.

### 타입이 누락을 막는다

한국어 사전이 **타입 원본**이다. 나머지 언어 사전은 그 타입을 만족해야 한다.

```text
한국어 사전 ──(타입 추출)──▶ 영어·일본어 사전이 만족해야 할 형태
```

키를 빠뜨리면 **컴파일이 실패한다.** 런타임에 빈 문자열이 뜨거나 키 이름이 그대로 노출되는 일이 구조적으로 불가능하다.

여기에 사전 정합성 테스트를 붙였다.

- 세 사전의 구조가 완전히 일치하는지
- 영어·일본어 사전에 한글이 남아 있지 않은지 (번역 누락 탐지)
- 인자를 받는 문구는 실제로 호출해서 결과를 확인

### 도메인은 문장을 들고 있지 않다

다국어를 넣으면서 계층 규칙이 한 번 더 검증됐다.

도메인 계층은 "이름이 비어 있습니다" 같은 **문장을 반환하지 않는다.** 코드만 돌려주고, 화면이 그 코드를 번역한다.

```text
도메인:  { 오류코드: 이름_없음 }
화면:    코드 → 현재 언어의 문장
```

알림 문구도 마찬가지다. 알림 계획을 세우는 순수 함수는 **문구를 밖에서 받는다.** 도메인이 언어를 알게 되는 순간 순수성이 깨지기 때문이다.

이 구조 덕분에 다국어를 나중에 추가했는데도 도메인 계층은 거의 손대지 않았다. **계층 분리가 실제로 값을 한 사건**이었다.

### 사용자의 선택이 항상 이긴다

첫 실행은 기기 언어를 따르고, 한 번 고르면 그 선택이 기기 언어보다 우선한다. 기기는 선호 언어를 순서대로 알려주므로 그중 지원하는 첫 번째를 쓰고, 지역 코드는 떼고 본다 (`en-US`와 `en-GB`는 이 앱에서 같다).

날짜·시간 선택창의 로케일도 앱 언어를 따르게 했다. 앱은 일본어인데 달력만 한국어로 뜨는 상태를 만들지 않기 위해서다.

그리고 **기록한 내용(이름·메모)은 번역하지 않는다.** 사용자가 쓴 그대로 둔다. 당연해 보이지만 명시적으로 규칙에 적어뒀다.

## 9. 트러블슈팅

실제로 막혔고, 원인까지 찾아서 해결한 것들이다.

### 9-1. 안드로이드에서 연락처 가져오기가 통째로 거부됐다

**증상.** iOS에서 잘 되던 연락처 조회가 안드로이드에서 아무것도 반환하지 않고 실패했다. 생일 하나가 아니라 **호출 전체**가 거부됐다.

**원인.** 요청할 필드 목록에 생일을 넣었는데, **안드로이드 쪽 네이티브 필드 열거형에는 그 값이 없었다.** 존재하지 않는 값이라 네이티브 변환 단계에서 실패하고, 그 결과 조회 요청 자체가 거부된 것이다. 오류 메시지에 필드 이름이 나오지 않아서 원인이 바로 보이지 않았다.

**해결.** 라이브러리의 안드로이드 네이티브 소스(Kotlin 열거형 정의)를 직접 열어 확인했다. 플랫폼별로 요청 필드를 나눴다.

| 플랫폼 | 생일을 얻는 방법 |
| --- | --- |
| iOS | 전용 생일 필드를 요청 |
| Android | 날짜 목록을 받아 라벨이 생일인 항목을 골라낸다 |

**배운 것.** 크로스 플랫폼 라이브러리의 타입 정의가 두 플랫폼 모두에서 동작한다는 보장이 아니다. **타입이 통과했다고 런타임이 통과하는 게 아니다.** 그리고 막혔을 때 네이티브 소스를 읽는 게 가장 빠른 길일 때가 있다.

### 9-2. 폐기된 API가 경고가 아니라 예외를 던졌다

**증상.** SDK를 최신 버전으로 올린 뒤 연락처 조회에서 런타임 예외가 발생했다.

**원인.** 널리 쓰이던 조회 API가 폐기(deprecated)를 넘어 **호출 시 예외를 던지도록** 바뀌어 있었다. 검색으로 나오는 예제 코드는 대부분 구버전 기준이라 도움이 되지 않았다.

**해결.** 새 API로 교체하면서 반환 형태가 바뀐 부분을 함께 조정했다. 여기서 **월 값의 기준이 0부터에서 1부터로 바뀐 것**도 발견했다. 이건 예외를 던지지 않아서 더 위험했다. 그대로 뒀으면 **모든 사람의 생일이 한 달씩 밀렸을 것이다.**

**배운 것.** 조용히 틀리는 변경이 시끄럽게 실패하는 변경보다 위험하다. 마이그레이션할 때는 **값의 의미가 바뀐 곳**을 특히 봐야 한다.

### 9-3. SQLite의 CHECK 제약조건이 NULL을 통과시킨다

**증상.** 제약조건을 걸어뒀는데 잘못된 조합의 데이터가 들어갔다.

**원인.** SQLite의 `CHECK`는 결과가 **FALSE일 때만** 막고, **NULL이면 통과**시킨다. 3값 논리(three-valued logic)다.

```sql
CHECK (direction IN ('given', 'received'))
-- direction 이 NULL 이면 이 식은 FALSE 가 아니라 NULL → 통과된다
```

의도는 "이 컬럼은 두 값 중 하나여야 한다"였는데, 실제로는 "NULL이거나 두 값 중 하나"가 되어 있었다.

**해결.** NULL이 될 수 있는 컬럼은 비교 전에 `IS NOT NULL`로 먼저 거르도록 모든 제약조건을 수정했다. 그리고 이 함정을 **스키마 파일 주석에 직접 적어뒀다.** 다음에 컬럼을 추가하는 사람(미래의 나 포함)이 같은 실수를 하지 않도록.

**배운 것.** 제약조건도 테스트해야 한다. "걸어놨으니 되겠지"가 통하지 않는다. 이 발견이 **스키마 검증 스크립트를 만든 계기**가 됐다.

### 9-4. 오전 약속이 전날 칸에 그려졌다

**증상.** 캘린더 탭에서 오전 시간대 약속만 하루 전날에 표시됐다.

**원인.** 약속 시각은 UTC로 저장된다. 달력에 그릴 때 그 문자열의 앞 10자를 잘라 날짜로 썼는데, 한국 시간 기준 **오전 9시 이전 약속은 UTC로는 전날**이다.

```text
저장: 2026-08-14T00:30:00Z   (한국시간 8월 14일 오전 9:30)
문자열 자르기 → "2026-08-14"   ... 이 경우는 맞다

저장: 2026-08-13T23:30:00Z   (한국시간 8월 14일 오전 8:30)
문자열 자르기 → "2026-08-13"   ... 하루 전날 칸에 그려진다
```

**해결.** 문자열을 자르지 않고, 시각을 **기기 로컬 시간대로 해석해서** 날짜와 시간으로 나누는 전용 함수를 만들어 캘린더·상세·수정 화면이 모두 이것을 쓰게 했다.

**배운 것.** "저장은 UTC, 표시는 로컬"이라는 원칙 자체는 알고 있었다. 문제는 **문자열 조작이 그 원칙을 조용히 우회한다는 것**이었다. ISO 문자열은 사람이 읽을 수 있게 생겨서 그냥 잘라 쓰고 싶어진다. 시간대 변환은 반드시 날짜 객체를 거치게 해야 한다.

### 9-5. 릴리스 빌드가 알 수 없는 네이티브 오류로 깨졌다

**증상.** 안드로이드 릴리스 빌드가 네이티브 이미지 변환 단계에서 실패했다. 오류 메시지에는 JS 코드와 아무 관련 없는 내부 도구 이름과 깨진 인자가 찍혔다.

**원인.** 빌드 도구가 **JDK의 출력을 파싱해서 버전을 읽어** 내부 도구에 인자로 넘긴다. 그런데 설치된 JDK 하나가 실행할 때마다 표준 출력으로 경고 문구를 뿜고 있었고, 그 문구가 버전 자리에 끼어들어 인자가 깨진 것이다.

원인이 **JS도 네이티브 코드도 아니고 JDK의 출력**이었다는 게 찾기 어려웠던 이유다.

**해결.** 출력이 깨끗한 JDK를 지정했다. 그리고 확인 방법을 문서화했다 — **표준 출력이 비어야 한다.** 표준 오류로 가는 메시지는 파싱 대상이 아니라 문제가 되지 않는다.

**두 번째 함정.** 처음에는 이 설정을 네이티브 프로젝트 폴더의 설정 파일에 적었다. 그런데 그 폴더는 **네이티브 재생성 시 통째로 다시 만들어진다.** 설정이 조용히 사라지고, 그다음 릴리스 빌드에서 같은 오류가 다시 났다. 캐시된 중간 결과가 남아 있으면 한동안 성공하다가 뒤늦게 터져서 원인을 되짚기도 어려웠다.

**해결.** 사용자 홈의 전역 설정에 적었다. 재생성의 영향을 받지 않는 위치다. 이 내용을 릴리스 문서에 경고와 함께 남겼다.

**배운 것.** **생성되는 디렉터리에 수동 설정을 넣으면 안 된다.** 그리고 "한동안 잘 되다가 갑자기 깨진다"는 대체로 캐시가 사라진 시점이라는 신호다.

### 9-6. 구독을 바꾸면 결제가 두 번 나갈 수 있었다

**발견.** 실제로 터진 게 아니라 결제 흐름을 설계하다 발견했다. 중간 요금제를 쓰는 사람이 상위 요금제 버튼을 누르면, 그냥 구매할 경우 **구독이 두 개가 되고 매달 두 번 청구된다.** 스토어는 이것을 막아주지 않는다.

**원인.** 안드로이드는 새 구독을 살 때 **"무엇을 대체하는지"를 함께 넘겨야** 기존 구독을 교체한다. 넘기지 않으면 별개의 구독이 생긴다. (iOS는 같은 구독 그룹에 넣어두면 자동 처리된다 — 플랫폼마다 해법이 다르다는 것도 함정이었다.)

**해결.** 세 겹으로 처리했다.

**① 방향에 따라 다르게 처리한다.**

| 방향 | 처리 | 사용자가 겪는 일 |
| --- | --- | --- |
| 업그레이드 | 즉시 전환 + 남은 기간 환산 | 바로 쓸 수 있고 **추가 청구 없음** |
| 다운그레이드 | 기간 종료 후 전환 | 결제한 기간은 그대로 쓰고 다음 결제부터 변경 |

업그레이드에서 차액을 즉시 청구하는 방식도 있었지만 고르지 않았다. 버튼 한 번에 예상 못 한 금액이 빠져나가는 것보다 남은 기간을 환산해주는 편이 놀랄 일이 없다. 다운그레이드를 즉시 처리하면 이미 결제한 기간을 빼앗는 셈이라 미룬다.

**② 바꾸기 전에 확인을 받는다.** 무엇이 언제 바뀌고 돈이 어떻게 되는지 먼저 보여준다. 결제는 되돌리기 번거로운 일이라 "눌러보고 알게 되는" 상황을 만들지 않는다.

**③ 기존 구독을 알아내지 못하면 진행하지 않는다.** 대시보드 설정 상태에 따라 현재 구독이 무엇인지 판별하지 못할 수 있다. 그때는 **구매를 진행하지 않고** 스토어에서 정리하도록 안내한다. 모르는 상태로 사면 구독이 두 개가 될 수 있고, **돈이 두 번 빠지는 것보다 안내가 낫다.**

방향 판단은 순수 함수로 분리해서 **실제 결제 없이 테스트**된다.

**배운 것.** 결제는 되돌리기 어려운 도메인이라 "일단 해보고 고친다"가 통하지 않는다. 사용자 돈이 걸린 곳에서는 **모르면 멈추는 것**이 옳은 기본값이다.

### 9-7. 결제 SDK를 언제 초기화할 것인가 — 복구 불가능한 상태를 만들 뻔했다

**문제.** 결제 SDK를 초기화하는 순간 사업자 서버에 요금제를 확인하러 간다. 아무것도 구매하지 않은 대다수 사용자에게는 확인할 게 없는 불필요한 통신이다. 그래서 **한 번이라도 구매한 사람에게만** 초기화하기로 했다.

여기서 "한 번이라도 구매한 사람"을 어떻게 판단하느냐가 문제였다.

**함정.** 처음에는 **현재 유효한 요금제**를 기준으로 삼으려 했다. 그런데 이러면 이런 일이 생긴다.

```text
1. 월 구독이 실제로는 정상 갱신됐다
2. 그런데 앱은 캐시된 옛 만료일만 보고 있다
3. 유예 기간이 지나자 무료로 강등한다
4. 강등됐으므로 "구매한 적 없는 사람"이 되어 확인을 멈춘다
5. → 실제로 돈을 내고 있는데 되돌아올 경로가 사라진다
```

**해결.** 판단 기준을 **저장된 구매 이력 자체**로 바꿨다. 만료로 강등됐어도 "산 적이 있는 사람"이라는 사실은 남는다. 그 사람은 계속 확인 대상이다.

**남은 대가.** 기기를 바꾸면 새 기기의 캐시가 비어 있어 자동 감지가 안 된다. 요금제 화면을 열면 그때 확인하므로 대부분 자연히 해결되고, 안 되면 '구매 내역 불러오기'로 복구된다. **완벽하지 않지만 어디가 뚫려 있는지 알고 있는 상태**로 남겼다.

그리고 이 조건은 개인정보처리방침과 스토어 데이터 안전성 신고에 그대로 반영되어 있다. **바꾸면 두 문서를 함께 고쳐야 한다**는 것을 코드 주석에 남겼다.

**배운 것.** 최적화가 상태 판단과 얽히면 복구 불가능한 상태를 만들 수 있다. **"이 조건이 false가 됐을 때 다시 true가 될 경로가 있는가"** 를 물어야 한다.

### 9-8. 다크 모드에서 차트 색이 눈을 찌른다

**증상.** 라이트 모드에서 잘 보이던 브랜드 강조색을 다크 모드 차트 막대에 그대로 썼더니 넓은 면적에서 지나치게 튀었다.

**원인.** 브랜드 강조색은 버튼이나 아이콘 같은 **작은 면적** 기준으로 고른 색이다. 차트 막대처럼 큰 면적을 채우면 밝기 대역이 맞지 않는다.

**해결.** 강조색과 차트용 색을 **디자인 토큰 수준에서 분리**했다. 라이트·다크 양쪽에서 밝기 대역과 배경 대비를 모두 확인한 값으로 정했다.

관련해서 관계 온도는 **색상만으로 표현하지 않는다**는 규칙도 지켰다. 항상 숫자와 문구를 함께 쓴다. 색각 이상 사용자를 고려한 것이기도 하고, "빨간색 = 나쁜 관계"로 읽히는 것을 피하려는 제품 원칙이기도 하다.

### 9-9. 같은 규칙이 두 곳에 존재하는 문제

**상황.** 요금제 권한 판정 로직이 앱(TypeScript)과 서버 함수(Deno 런타임) 양쪽에 필요했다. 런타임이 달라서 앱 코드를 그대로 가져올 수 없었다.

**위험.** 한쪽만 고치면 **"앱에서는 유료인데 백업은 거부되는"** 상태가 된다. 사용자 입장에서는 돈을 냈는데 기능이 안 되는 것이고, 원인을 짐작하기도 어렵다.

**대응.** 없앨 수 없는 중복이라면 **눈에 띄게 만들었다.**

- 양쪽 파일 주석에 "반드시 함께 고친다"를 명시
- 유예 기간 같은 상수는 앱 · 서버 함수 · DB 함수 세 곳에서 같은 값이어야 함을 문서화
- 서버 함수를 굳이 **하나로 합쳤다.** 웹훅용과 앱용을 나누면 같은 판정 로직이 또 복사되기 때문이다. 역할은 파일이 아니라 **"부르는 쪽이 무엇으로 인증하는지"** 로 구분하게 했다.

**배운 것.** 모든 중복을 제거할 수는 없다. 제거할 수 없는 중복은 **최소화하고, 문서화하고, 어긋났을 때 어떻게 되는지를 적어두는 것**이 현실적인 대응이다.

### 9-10. 인증 토큰이 보안 저장소에 다 안 들어갔다

**증상.** 로그인 세션이 간헐적으로 유지되지 않았다.

**원인.** OS 보안 저장소(Android Keystore / iOS Keychain)에는 **값 길이 제한**이 있다. 인증 토큰이 그 한도를 넘었다.

**해결.** 값을 나눠 담고 읽을 때 다시 합치도록 했다. 평문으로 저장되는 일반 저장소를 쓰는 선택지는 처음부터 배제했다. **인증 토큰을 평문으로 두는 것은 타협 대상이 아니라고 봤다.**

**배운 것.** 플랫폼 보안 API에는 크기 제약이 따라온다. 짧은 값으로 테스트하면 안 보이는 문제다.

### 9-11. 달력 높이가 달마다 덜컥거렸다

**증상.** 달을 넘길 때 아래 내용이 위아래로 튀었다.

**원인.** 달에 따라 달력이 5주가 되기도 하고 6주가 되기도 한다. 필요한 만큼만 그리면 높이가 달라진다.

**해결.** **항상 6주(42칸) 고정**으로 그리고, 앞뒤로 남는 칸은 이전·다음 달 날짜로 채운다. 레이아웃이 흔들리지 않는다.

달력 라이브러리를 쓰지 않은 이유는, 필요한 계산이 파일 하나 분량이었고 앱의 차분한 톤에 맞추려면 직접 그리는 편이 나았기 때문이다. 격자 계산은 UTC 자정 기준으로 다뤄서 시간대나 서머타임에 날짜가 밀리지 않게 했다. (9-4에서 배운 것을 적용한 부분이다.)

## 10. 테스트 전략

### 무엇을 테스트했나

**도메인 로직 전 영역.** 33개 스위트 / **514개 케이스가 전부 통과**한다.

```text
온도       초기값 · 종류별 가중치 · 상한/하한 · 반복 교류 · 월간 감소 · 경계 조건
생일       D-day · 올해 지난 생일 · 윤년 2/29 · 미입력 · 잘못된 날짜
약속       상태 전이 · 시간대 분리 · 중복 연결 방지
통계       월 경계 · 기간 집계 · 심층 분석
캘린더     6주 격자 · 월 넘김 · 앞뒤 달 채움
알림       무엇을 언제 · 개수 상한 · 권한 없음 상태
결제       요금제 권한 · 만료/유예 · 전환 방향 · 외부 응답 매핑 · 값 검증
다국어     사전 구조 일치 · 번역 누락 탐지 · 인자 문구 실제 호출
데이터     매핑 · 쿼리 · 마이그레이션 · 백업 형식 · 변경 감지 · 오류 변환
설정       환경 변수 검증 (비밀 키 거부 포함)
```

### 테스트가 쉬웠던 이유는 설계 덕분이다

도메인이 순수하고 현재 시각을 주입받기 때문에, 테스트가 시간에 의존하지 않는다. 목(mock)이 거의 필요 없다.

```text
// 3년 뒤 상태를 검증하는 것도 그냥 인자다
계산({ ..., 기준일: '2029-08-11' })
```

이건 우연이 아니라 **테스트 가능성을 위해 아키텍처를 그렇게 정한 결과**다. 그리고 린트가 그 구조를 유지시킨다.

### 통합 테스트의 공백을 인정했다

네이티브 모듈 때문에 저장소 계층의 실기기 통합 테스트는 아직 없다. 이걸 **"없다"고 문서에 적어뒀다.**

대신 스키마 검증 스크립트로 **제약조건이 실제 SQLite 엔진에서 의도대로 동작하는지**는 확인한다. 완전한 대체는 아니지만, 가장 위험한 부분(무결성)은 덮는다.

### 출시 전 체크리스트를 세 분류로 나눴다

| 분류 | 의미 | 예 |
| --- | --- | --- |
| **막는 것** | 이거 없이 출시하면 문제가 생긴다 | 실기기 결제 전 구간 검증, 스토어 신고 양식 갱신 |
| **권장** | 없어도 출시되지만 나중에 비싸진다 | 오류 모니터링, 대량 연락처 성능 확인 |
| **알고 출시하는 것** | 의도된 범위 밖 | 레코드 단위 동기화 없음, iOS 없음 |

세 번째 분류를 명시적으로 만든 게 유용했다. **"안 한 것"과 "못 한 것"과 "안 하기로 한 것"은 다르다.**

## 11. 의도적으로 하지 않은 것

기능을 넣지 않은 것도 결정이다. 각각 이유가 있다.

| 하지 않은 것 | 이유 |
| --- | --- |
| 레코드 단위 클라우드 동기화 | 삭제 기록(tombstone) 설계가 먼저 필요하다. 지금은 하드 삭제라 그대로 붙이면 **지운 사람이 되살아난다.** 백업/복구만으로도 "기기를 바꿔도 데이터가 산다"는 가치는 전달된다 |
| 자동 통화/메시지 기록 수집 | 기술적으로 가능해도 이 앱의 개인정보 원칙과 정면으로 충돌한다 |
| 주소록 전체 자동 등록 | 연락처와 관계는 다른 개념이라는 제품의 핵심 전제를 무너뜨린다 |
| 완료 약속의 만남 자동 전환 | 기록하지 않은 사실이 데이터에 섞이고 온도에 반영된다 |
| 상태 관리 라이브러리 | 지금 규모에서 필요하지 않았다. 필요해지면 그때 넣는다 |
| 번역 라이브러리 | 타입 강제 사전으로 **더 강한 보장을 더 적은 의존성으로** 얻었다 |
| 달력 라이브러리 | 필요한 것이 파일 하나 분량이었고, 앱의 톤에 맞추려면 직접 그리는 편이 나았다 |
| 차트 라이브러리 | 이미 있는 SVG 렌더러로 충분했다. 새 네이티브 의존성을 늘리지 않았다 |
| 게임화 / 배지 남발 | 관계를 점수 경쟁으로 만들지 않는다는 제품 원칙 |

패키지를 추가하기 전에 항상 네 가지를 확인했다. ① 플랫폼이 이미 제공하는가 ② 설치된 패키지로 되는가 ③ 유지보수성과 네이티브 빌드 영향은 어떤가 ④ 최소한만 추가하는가.

파일 선택 기능도 이미 설치된 파일 시스템 모듈의 API로 해결해서 별도 패키지를 넣지 않았다.

## 12. 회고

### 잘한 결정

**규칙을 도구로 강제한 것.**
문서에 적은 규칙은 잊히지만 린트 규칙은 잊히지 않는다. 도메인 순수성과 개인정보 로깅 금지를 규칙으로 만든 덕분에, 기능을 계속 추가하는 동안에도 구조가 무너지지 않았다.

**도메인 모델을 갈아엎은 것.**
온도가 천장에 붙는 문제를 발견했을 때, 가중치만 조정하고 넘어갈 수도 있었다. 파라미터가 아니라 모델을 고친 게 맞았다. 그때 안 고쳤으면 **출시 후 사용자 데이터가 쌓인 상태에서** 고쳐야 했을 것이다.

**"모르는 것"을 문서에 남긴 것.**
무제한 요금제에서 친구 리스트를 어떻게 할지, 기기를 바꿨을 때 결제 자동 감지가 안 되는 것 같은 미해결 지점을 숨기지 않고 적었다. 알면서 남겨둔 부채는 관리할 수 있지만 모르는 부채는 그럴 수 없다.

### 다시 한다면

**스키마 검증을 더 일찍 만들었을 것이다.**
CHECK 제약조건의 NULL 통과 문제는 검증 스크립트를 만들고 나서야 발견했다. 그전까지 제약조건이 동작한다고 **믿고 있었다.**

**오류 모니터링을 처음부터 넣었을 것이다.**
지금은 개발 빌드에서만 로그가 남는다. 출시 후 사용자 기기에서 무슨 일이 일어나는지 알 방법이 없다는 게 남은 가장 큰 공백이다. 다만 이 앱에서는 **어떤 정보를 수집할지가 개인정보 문제와 직결**되어서, 개인정보처리방침과 함께 설계해야 하는 항목이다.

**실기기 검증 시점을 앞당겼을 것이다.**
연락처 API 문제와 캘린더 시간대 문제 모두 실기기에서만 드러났다. 에뮬레이터와 단위 테스트로 잡히지 않는 종류의 버그가 있다.

### 이 프로젝트에서 얻은 것

기술 스택을 익힌 것보다, **판단의 기준을 세우고 그 기준을 코드와 문서에 남기는 연습**이 된 프로젝트였다.

- 사람의 관계를 숫자로 바꾸는 규칙을 정하고, 틀렸을 때 모델 수준에서 다시 세우는 일
- 오프라인 동작을 지키기 위해 어느 위조까지 허용할지 **명시적으로 결정**하는 일
- 돈이 걸린 흐름에서 "모르면 멈춘다"를 기본값으로 두는 일
- 안 한 일을 "못 한 것"과 "안 하기로 한 것"으로 나눠 적는 일

코드는 다시 쓸 수 있지만 이런 판단의 흔적은 그 프로젝트에만 남는다. 그래서 이 문서를 남긴다.
