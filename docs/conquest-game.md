## 1. 프로젝트 개요와 설계 원칙

### 1-1. 어떤 게임인가

내 영토는 초당 병력을 자동 생산한다. 영토를 누른 채 목표로 드래그해 손을 떼면 병력이 출발하고,
거리에 비례한 이동 시간이 지난 뒤 도착해서야 전투가 벌어진다. 점령하면 생산량이 늘고,
늘어난 생산량으로 더 큰 공격을 한다. **이 루프가 게임의 전부**이고, 나머지 시스템은 전부 이 루프를
강화하는 부가 요소로 취급했다.

이 위에 네 겹의 규칙이 순서대로 얹힌다.

| 겹 | 규칙 | 플레이어가 새로 하게 되는 판단 |
|---|---|---|
| 1 | 영토 레벨(생산량·상한 6단계) | 어디를 키우고 어디를 버릴 것인가 |
| 2 | 버프 영토 3종 · 대포 영토 | 어떤 땅이 값진가 |
| 3 | 보급선 · 시야 · 이동불가지형 | 전선을 어디까지 밀 것인가, 모르는 곳에 밀어 넣을 것인가 |
| 4 | 인접 공격 제한 · 행동력 | 지금 칠 것인가, 모을 것인가 |

### 1-2. 프로젝트 규칙

작업 내내 지킨 다섯 가지다. 문서에 먼저 적고 그대로 지켰다.

1. **기존 코드를 먼저 확인한다** — 새 구조를 만들기 전에 같은 일을 하는 것이 이미 있는지 찾는다.
2. **최소한의 변경으로 구현한다** — 규칙이 추가돼도 기존 콘텐츠의 코드 경로는 그대로 둔다.
3. **한 클래스는 한 책임만 갖는다** — 큰 스크립트보다 역할별 작은 스크립트를 선호한다.
4. **게임 로직과 UI 로직을 분리한다** — UI는 규칙을 모르고, 규칙은 화면을 모른다.
5. **하드코딩보다 설정 가능한 구조** — 밸런스 수치는 전역 설정 한 곳, 콘텐츠 구성은 데이터로.

이 원칙이 실제로 값을 한 지점들은 각 장에서 표시했다.

## 2. 아키텍처

### 2-1. 씬 구성

```
[스플래시] → [로비]  ─(스테이지 선택 / PLAY 모달)→  [인게임]
                │                                        │
        모달 다수(상점·패스·프로필·길드·친구·랭킹 등)     ├─ 월드: 영토 컨테이너 · 병력 · 지형/보급 오버레이
        전부 로비가 미리 적재해 한 번에 컴파일된다         ├─ 규칙 모듈: 보급 / 시야 / 경로
                                                          ├─ AI · 입력 매니저 · 카메라
                                                          └─ HUD (CanvasLayer)
```

- **월드와 UI를 분리**한 것이 카메라 팬·줌, 세로 모드, 시야 셰이더를 모두 가능하게 한 전제다.
  월드는 Camera2D 아래 월드 좌표계, UI는 CanvasLayer의 화면 좌표계에 있다.
- 화면 좌표 ↔ 월드 좌표 변환은 캔버스 변환의 역행렬 한 번으로 처리해, 줌·팬 상태와 무관하게
  터치 지점이 항상 올바른 영토를 가리킨다.

### 2-2. 전역 상태(Autoload) 8종

| 성격 | 보관하는 것 |
|---|---|
| 밸런스 설정 | 생산 속도, 상한, 거리 단위, 행동력, 제한 시간 등 튜닝 대상 수치 전부 |
| 사용자 설정 | 사운드, 화면 방향 등 씬과 무관한 값 |
| 진행도 저장 | 스테이지 클리어 기록, 모드별 난이도 파생 |
| 소유물 | 재화, 경험치·레벨, 하트, 프로필, 보유 스킨 |
| 패스 진행도 | 시즌마다 초기화되는 값이라 소유물과 **의도적으로 분리**하고 저장 파일도 따로 둔다 |
| 세션·요청 창구 | 로그인, 토큰 갱신, 인증 헤더, 재시도 |
| 실시간 소켓 | 소켓 하나 + 토픽 여러 개 + 재연결 |
| 결제 | 스토어 플러그인을 만지는 유일한 자리 |

**설계 판단 두 가지가 여기 들어 있다.**

- **값과 정의를 분리한다.** 값은 Autoload가 들고, "상품표·보상표·랩업 정의" 같은 것은 별도 정의
  스크립트가 들고, 화면은 그리기만 한다. 그래서 상점·패스·결과 화면이 같은 표를 보고 수치가
  갈라지지 않는다.
- **순환 의존을 구조로 막았다.** Autoload가 참조하는 정의 스크립트는 그 Autoload를 되참조하지
  않는다. 되참조하면 Autoload 등록 이전 시점에 컴파일되며 식별자를 찾지 못해 프로젝트 전체가
  열리지 않는다. 필요한 값은 **인자로 받게** 만들었다.
- 등록 순서에 의미가 있는 곳이 한 군데 있다(패스 진행도가 경험치 획득 신호를 구독하므로 소유물보다
  뒤에 있어야 한다). 순서 의존은 이 한 곳으로 제한했다.

### 2-3. 상태 변경의 단일 진입점

상태를 바꾸는 요청은 **함수 호출이 아니라 데이터 객체**로 표현한다.

```
입력 매니저 ─┐
             ├─► 공격 커맨드(출발 id, 목표 id, 비율) ─► 게임 매니저(제출 진입점) ─► 판정/적용
AI       ────┘
튜토리얼 검사 ◄── 제출 신호를 구독
```

- 커맨드는 **노드 참조가 아니라 정수 id**를 담는다. 노드 참조는 전송할 수 없고, id 기반이면
  양쪽에 같은 id 체계만 있으면 된다.
- 이 경계 덕분에 **입력·AI·튜토리얼이 같은 문을 쓴다.** 튜토리얼이 "지정한 경로로 실제로 보냈는가"를
  검사할 수 있는 것도 제출이 신호로 방송되기 때문이다.
- 비용이 거의 들지 않는 습관인데, 나중에 판정 로직을 다른 실행 주체로 옮길 때 호출부를 건드릴
  필요가 없다. **지금 값을 하는 부분(공유 진입점)만 취하고, 값이 불확실한 부분(커맨드 큐, 틱 기반
  처리, 다중 매치 인스턴스화)은 만들지 않았다** — 검증할 대상이 없는 상태에서 미리 만들면 실제
  요구와 어긋날 위험이 크다.

## 3. 게임 코어 설계

### 3-1. 인접 그래프 — 이미 있던 것을 규칙으로 승격

**문제.** 판 중반이 되면 맵 곳곳에서 공격이 오가 화면이 이동선으로 뒤덮였다. 모바일에서 가볍게
즐기기 어렵고 캐주얼한 톤과도 맞지 않았다.

**원인.** 공격 적용부에 **거리 검사가 아예 없었다.** 어떤 영토든 맵 반대편을 칠 수 있었다.
AI도 맵 전체를 후보로 잡았고, 거리 가중치가 낮아 1200px 횡단이 큰 손해가 되지 않았다.

**해결.** 새 개념을 만들지 않고, **이미 화면에 그려지고 있던 보조선**을 규칙으로 승격했다.

> 두 영토는 표면 간격이 보급 사거리(100px) 이내면 **인접**하다.

이 그래프는 원래 세 곳에서 이미 쓰이고 있었다 — 화면의 흐린 안내 점선, 집결 경로 탐색, 맵 설계 시
전략 위상 지표(본진 사이 홉 수). **맵의 골격으로 이미 설계해온 것을 규칙 이름만 붙여 승격한 것**이다.

플레이어가 외울 것도 하나로 합쳐졌다 — **점선 하나가 "공격할 수 있는 길"이자 "보급선"이자
"집결 경로"다.**

구현 관점의 판단:

- 인접 목록은 맵 생성 시 **한 번만** 만든다. 점령으로 주인이 바뀌어도 좌표는 그대로라 다시 만들
  이유가 없다.
- 보급 모듈과 시야 모듈은 **일부러 캐시를 공유하지 않았다.** 같은 식을 같은 입력으로 계산하므로
  결과가 동일하고, 캐시를 쓰려면 두 모듈에 게임 매니저 의존을 새로 넣어야 한다. 얻는 것이
  성능뿐이라 값이 맞지 않는 거래였다.

### 3-2. 인접 제한은 공격에만 건다

| 대상 | 인접 필요 | 행동력 |
|---|---|---|
| 적 · 중립 (= 공격) | **필요** | **1** |
| 내 영토 (= 이동 · 지원 · 집결) | 불필요 | 0 |

이동까지 이웃으로 묶으면 결정이 늘지 않고 손가락 품만 는다. 반대로 공격까지 풀면 개편의 의미가
없다. **이 경계 덕분에 집결 기능이 예외 처리 없이 그대로 동작한다** — 3홉 뒤 영토에서 병력을
끌어와도 전부 아군 대상이라 판정을 그냥 통과한다.

그래서 원거리 공세는 **두 박자**가 된다: ① 뒤쪽에서 전선으로 모으기(제한 없음) → ② 전선에서
치기(인접 필수, 행동력 1). 이 두 박자를 만드는 것이 개편의 목적이었다.

**"인접하지 않은 출발지는 자동으로 중계해 준다"는 자동화는 넣지 않았다.** 편하긴 하지만
"모을까 / 지금 칠까"라는 결정 자체를 없앤다. 그 결정이 이번 개편으로 얻으려던 전략성의 본체다.

대신 **조용히 무시하지도 않았다** — 3-4 참조.

### 3-3. 행동력 — 세는 단위는 "명령"이 아니라 "제스처"

최대 3회 충전, 3초당 1회 회복, 판 시작 시 가득 찬 상태.

멀티드래그로 몇 곳에서 동시에 출발하든 플레이어는 **한 동작**을 했다. 그래서 차감을 개별 공격
적용부가 아니라 **배치(batch) 제출 진입점**에 뒀다.

```
배치 제출 → ① 규칙에 맞는 것만 남긴다
          → ② 적·중립 대상이 하나라도 있으면 공격 배치로 보고 행동력 1을 요구
          → ③ 실제로 한 부대라도 나갔을 때만 차감
```

- 전부 아군 대상이면 차감하지 않는다(이동·지원은 무료).
- 여러 손가락을 한꺼번에 터뜨리는 조작도 제스처 하나라 1회다.
- 단건 제출은 배치의 래퍼로 남겨 AI·튜토리얼 호환을 유지했다.
- **배치 하나 = (확장 시) 메시지 하나**라 전송 단위와도 자연스럽게 맞는다.

**AI는 행동력을 쓰지 않는다.** AI에는 이미 판단 주기(3초)와 턴당 최대 실행 수라는 같은 역할의
제약이 있고, 게이지까지 물리면 매 턴 굶는다.

### 3-4. 체류 충전 — 기준을 "총 홀드"에서 "목표 위 체류"로

기존에는 누른 순간부터의 총 시간으로 파병 비율을 정했다. 그러면 먼 목표까지 끌고 가는 동안
저절로 충전돼서 **가까운 곳을 칠 때만 손해**였다.

```
목표 위 체류 < 0.8초  → 50% (기본)
목표 위 체류 ≥ 0.8초  → 0.5초마다 +10%, 최대 100% (2.8초에 100%)
```

손가락 아래 영토가 바뀌면 체류 시간이 0으로 돌아간다 — **목표를 옮기면 충전도 처음부터다.**
기존 홀드 타이머는 더블탭 판정이 계속 쓰므로 **두 타이머를 분리해서** 유지했다(하나로 합쳤다면
더블탭 메뉴가 깨졌을 것이다).

현재 % 라벨은 월드가 아니라 HUD에 그린다. 화면 좌표여야 손가락을 정확히 따라간다. **행동력이
모자라면 라벨이 무채색으로 떠서 "지금 떼도 안 나간다"를 미리 알린다.**

### 3-5. 못 보내는 출발지를 보이게 하기

처음에는 목표와 인접하지 않은 출발지의 선택 표시를 그냥 껐다. 그랬더니 여러 영토를 훑어 적을 쳤을 때
**뒤쪽 영토가 아무 설명 없이 풀려서** 왜 빠졌는지 알 수 없다는 피드백이 왔다.

끄는 대신 상태를 하나 더 뒀다.

| 상태 | 표시 | 뜻 |
|---|---|---|
| 선택됨 | 흰 원(채움) | 손을 떼면 여기서 나간다 |
| 목표 | 주황 원(채움) | 여기로 간다 |
| **못 감** | **회색 빈 고리 + ✕ 배지** | 잡혀는 있지만 이 목표엔 길이 없다 |

- **채운 원 / 빈 고리**로 갈라야 한눈에 구분된다. 처음엔 빗금 하나만 그었는데 삐져나온 선처럼
  보여 뜻이 읽히지 않았다.
- **목표가 정해지기 전에는 판단하지 않는다.** 빈 땅 위를 지나는 동안에는 전부 선택 상태로 두고,
  목표가 잡히는 순간 갈린다.
- **표시와 실제 발사가 같은 판정 함수를 공유**하므로 화면과 결과가 어긋날 수 없다.

### 3-6. 상한 초과와 감쇠

병력 상한을 넘겨 합류하는 것을 허용하되, 유예 시간이 지나면 서서히 감쇠한다. 병력이 **도착할
때마다** 유예가 리셋되므로, 여러 곳에서 집결해 상한을 넘겨 모아도 마지막 도착 후 유예가 온전히
남는다.

**"전선 영토는 초과 병력이 줄지 않는다" 같은 예외는 일부러 넣지 않았다.** 최전선이 상한을 넘겨
버티는 임시 요새가 되어, 상한을 레벨과 무관하게 통일해 없앴던 "웅크리기" 전략이 그대로 되살아난다.

## 4. 맵 파이프라인 — 스케치를 검증 가능한 데이터로

### 4-1. 두 가지 맵

| 방식 | 쓰는 곳 | 특징 |
|---|---|---|
| **절차 생성** | 초반 진행 스테이지 | 스테이지 번호를 시드로 좌표 생성. 배치 제약(겹침·지형·연결성)을 만족할 때까지 재시도 |
| **고정 좌표** | 자유 대전·실전연습 공용 맵 4장, 튜토리얼 24판 | 데이터로 좌표를 직접 들고 있다. 기기·해상도와 무관하게 항상 같은 맵 |

고정 맵 좌표는 **정규화(0~1) 값**으로 저장한다. 맵 크기를 바꿔도 배치 비율이 유지된다.
반대로 튜토리얼 맵은 **픽셀 좌표로 적고 변환기가 정규화한다** — 정규화 좌표를 손으로 계산하면
읽을 수도 고칠 수도 없기 때문이다. 같은 데이터 구조를 쓰되 **작성 편의를 기준으로 입력 형식을
갈랐다.**

### 4-2. 절차 생성의 배치 전략

무작위 좌표 + 거부 샘플링을 쓰면 조건을 못 맞출 때 **외딴 영토**가 생긴다. 그러면 아무 공격도
오갈 수 없는 죽은 영토가 된다.

그래서 무작위로 뽑아 검사하는 대신, **이미 놓인 영토 주변의 "사거리 고리" 안에 붙여 나가는** 방식을
썼다. 이렇게 하면 사거리 안에 이웃이 없는 영토가 **구조적으로 나오지 않는다.**

좌표는 노드를 만들기 전에 전부 계산해 두고, 연결 덩어리 개수를 세어 **가장 덜 쪼개진 배치를**
고른다. 디버그 빌드에서는 그래프가 쪼개지면 경고를 낸다 — 새 맵 좌표를 적을 때 바로 걸린다.

### 4-3. 손그림 스케치 → 맵 데이터 (고정 맵 4장)

가장 손이 많이 간 파이프라인이다.

```
① 사분면 손그림 스케치
       │  (맵 1~3: 사분면을 90도씩 4회전해 조립 → 점대칭이 구조적으로 보장됨)
       ▼
② 좌표 정규화 + 회전 변환   (x,y,w,h) → (1-y-h, x, h, w)
       │
       ▼
③ 겹침 완화 계산 — 스케치 위치를 목표로 "당기면서" 겹침만 밀어낸다
       │  스케치는 영토를 전부 같은 크기 원으로 그리지만 실제 반지름은 35~85다
       │  → 그대로 두면 큰 영토와 대포가 이웃·지형을 파고든다
       ▼
④ 정량 검증 (아래 표)
       │
       ▼
⑤ 통과하면 맵 데이터로 확정
```

**검증 항목과 실제 결과** (맵 2번 예시):

| 항목 | 값 | 기준 |
|---|---|---|
| 영토 간 최소 간격(표면) | 25.7px | 최소 간격 20 이상 |
| 영토 ↔ 지형 최소 여유 | 18.0px | 지형 여유 14 이상 |
| 맵 경계 최소 여유 | 20.0px | 0 이상 |
| 보급 그래프 연결 성분 | **1개** (이웃 최소 1 / 평균 2.7) | 전부 하나로 이어짐 |
| 정중앙 최상위 영토 | 이웃 4개, 최근접 95.5px | 사거리 100 이내 |
| 대포 사거리 안 영토 수 | 2개 | 다른 맵과 동일(밸런스 일치) |
| **통행 격자 도달성** | 빈 칸 844 = 도달 844 | 지형이 맵을 갈라놓지 않음 |

**여기서 얻은 교훈이 두 개 있다.**

1. **눈대중 격자로 검산하면 안 된다.** 실제 통행 판정은 격자 40px + 지형 부풀림 + 칸 중심 판정을
   쓴다. 20px 격자로 눈대중하면 "통과하는데 실제로는 막히는" 틈이 생긴다. **검산은 실제 통행
   모델과 같은 파라미터로 해야 한다.**
2. **모양 변형을 최소화하는 선택지를 고른다.** 맵 3번에서는 스케치대로면 큰 영토가 두 지형 사이
   통로 140px에 물리적으로 들어가지 못했다(필요 폭 158). 지형 띠를 좁히거나 자르는 대신
   **오른쪽으로 26px 옮기는** 안을 택했다 — 통로가 넓어지면서 지형 여유가 최대치에 도달했고
   원본 모양이 가장 덜 망가졌다.

맵 3번부터는 스케치에 **보급선까지 그려져 들어왔다.** 그 선을 픽셀 비율로 검출해 "이 둘은
사거리 안에 있어야 한다"는 제약으로 완화 계산에 넣었고, 지정된 10개 연결이 전부 유지됐다.

### 4-4. 튜토리얼 맵 설계 규칙

24판을 만들면서 정한 두 가지 규칙이 학습 효율을 좌우했다.

- **가르칠 대상은 본진 바로 옆에 둔다.** 배운 즉시 차지해 보게 하려는 것이다. 세 칸 건너에 두면
  도달하기 전에 왜 배웠는지 잊는다.
- **새 규칙을 소개하는 판은 지형 골격을 앞 판과 똑같이 둔다.** 바뀐 것이 하나뿐이어야 그게
  무엇인지 보인다.

또한 버프 종류를 무작위가 아닌 **고정 지정**으로 뒀다. 무작위로 두면 생산 버프를 가르치는 판에
이동속도 버프가 나올 수 있다.

지형을 쓰는 판(길을 좁혀 수업을 만드는 판)에서는 **막는 띠가 맵 가장자리까지 닿아야 한다.**
영토는 반지름 때문에 가장자리에 놓일 수 없지만 병력은 지날 수 있어서, 위쪽에 조금만 틈을 남겨도
경로 탐색이 그 틈으로 새고 "길이 하나"라는 수업이 깨진다.

## 5. 전략 규칙 3종 — 하나의 그래프 위에 쌓기

규칙마다 스크립트를 하나씩 두고, **스테이지 데이터의 플래그로 켜고 끈다.** 규칙이 꺼진 판은
기존 코드 경로가 그대로 유지된다.

| 규칙 | 데이터 | 로직 | 표시 |
|---|---|---|---|
| 보급선 | 불리언 플래그 | BFS | 밝은 파란 점선, 끊긴 영토는 옅은 물감 |
| 시야 | 불리언 플래그 | 시야 모듈 + 판정 API | 안개 셰이더 + 마지막 목격 상태로 정지 |
| 이동불가지형 | 정규화 사각형 + 종류 | 격자 A* + 직선 단축 | 강물/용암 그림 |

### 5-1. 보급선 — 연결 상태는 "지금" 판정한다

본진에서 시작해 같은 진영 영토를 사거리 이내로 타고 갈 수 있는가를 BFS로 본다. 닿지 못한 영토는
생산량이 절반이 된다.

- **"점령 당시"가 아니라 현재 연결 상태**로 판정한다. 그래서 점령·상실이 일어날 때마다 양쪽 진영을
  다시 계산한다. 영토 30개 기준 BFS 2회라 비용은 무시할 수준이다.
- 중간 영토를 빼앗기면 그 뒤쪽 전선이 한꺼번에 말라붙는다 — 이 규칙이 만드는 재미의 핵심이다.
- **본진을 빼앗기면 그 진영은 출발점이 없어져 전부 끊긴다.** 규칙을 문자 그대로 구현한 결과이고,
  "본진을 치면 상대 생산이 반으로 준다"는 강한 보상이 되기도 한다.

**규칙을 만들어 놓고 화면에 단서를 주지 않은 문제**도 여기서 다뤘다. 사거리 100이 실제로 어디까지인지
알 수 없어 "여기 먹으면 이어지나"를 눈대중해야 했다. 그래서 **소속과 무관하게 사거리 안에 있는 모든
쌍**을 아주 흐린 점선으로 잇는다.

- **정보 유출이 아니다.** 중립 영토 위치는 안개 아래에서도 항상 보이고, 보급 연결은 위치와 반지름만으로
  정해지는 **순수 함수**다. 이 그래프에는 플레이어가 이미 볼 수 있는 것 외의 정보가 하나도 없다.
- **색 선택에서 한 번 틀렸다.** 처음엔 흐린 흰색으로 뒀는데 인게임 배경이 밝아 전혀 보이지 않았다.
  잉크색(병력 숫자와 같은 톤)으로 바꾸니 두 배경 위에서 모두 읽혔다.
- 활성 보급선과 헷갈리지 않게 **점(dot)에 가깝게** 그려 위계를 만들었다. 33영토 맵에서 링크가
  60개까지 나오므로 이 정도로 가벼워야 화면이 지저분해지지 않는다.

### 5-2. 시야 — 표시와 판정을 분리한다

- **안개는 셰이더로 그린다.** 맵 전체를 덮는 사각형에 걸고 시야 원들을 uniform 배열로 넘겨 알파를
  깎는다. Godot 2D에는 "도형 빼기" 블렌드가 없어서 구멍을 뚫으려면 이 방법이 가장 단순하다.
  셰이더는 원뿐 아니라 **선분**도 구멍으로 받아, 보급으로 이어진 두 영토 사이 통로 전체가 열린다.
- **영토는 숨기지 않는다.** 중립 영토 위치는 안개 속에서도 보이고, 시야를 벗어난 영토는 **마지막으로
  본 상태에서 표시가 멈춘다.** 중립인 줄 알고 쳤다가 적 영토였다면 그때 본 병력 수 그대로 안개
  아래 남는다. 실제 상태는 계속 돌아가고 **화면 값만 얼린다.**
- **AI도 같은 제약을 받는다.** 플레이어만 눈을 가리면 난이도가 규칙과 무관하게 올라간다.
  **표시(시야 모듈)와 판정(게임 매니저의 가시성 API)이 분리돼 있어서 AI는 화면 상태를 몰라도 된다.**
  이 분리가 이 규칙에서 가장 값을 한 설계다.
- 갱신은 매 프레임이 아니라 0.1초 간격이다. 영토는 잘 안 바뀌고 병력은 천천히 움직인다.
- 이동 병력의 시야는 **현재 위치만** 비춘다. 병력 목록을 매번 다시 읽어 시야 원을 만들기 때문에
  지나간 자리가 영구히 열리지 않는 동작이 자연히 따라온다.

### 5-3. 이동불가지형 — 격자 A* + 직선 단축

- 데이터는 **맵 크기 대비 정규화 사각형 + 종류**이고, 항상 대칭 쌍으로 넣는다.
- **경로는 격자 A*(칸 40px)로 찾는다.** 사각형 장애물뿐이라 내비메시를 만들 이유가 없고,
  격자는 **결정론적**이라 같은 상황에서 항상 같은 경로가 나온다.
- **직선이 막히지 않으면 A*를 아예 돌리지 않는다.** 지형이 없는 판의 기존 직선 연출을 그대로
  유지하기 위해서다. 막힘 검사는 선을 12px 간격으로 찍어 사각형에 들어가는지 보는 방식이다.
- **격자 경로를 그대로 쓰면 계단처럼 여러 번 꺾인다**(실제로 점 11개가 나왔다). 그래서 A* 결과에
  **직선 단축(string pulling)**을 걸어 "막히지 않는 한 최대한 멀리 직선으로" 잇는다 →
  기획 의도대로 **출발 → 지형 옆 → 목적지로 두 번만 꺾인다.**
- 병력 이동 연출은 직선 보간에서 **폴리라인 추종**으로 바뀌었다. 구간별 누적 길이를 미리 만들어
  거리로 위치를 찾고, 점선·발자국·화살촉·유닛 방향이 전부 현재 구간을 따른다. 경로가 길어지면
  이동 시간도 그만큼 늘어난다(속도는 그대로).
- 출발·도착 칸이 예외적으로 막혀 있으면 직선으로 되돌린다 — **병력이 영원히 도착하지 않는 것보다 낫다.**

## 6. AI — 우선순위 트리를 버리고 점수식으로

### 6-1. 왜 트리를 버렸나

초기 버전은 우선순위 트리(1순위 중립, 2순위 플레이어…)였다. 이 방식은 **"플레이어 영토가 항상
존재해서 특정 순위가 절대 밀리지 않는"** 문제가 반복됐다. 그래서 모든 후보를 **같은 점수식으로**
평가하고 최고점을 실행하는 방식으로 전환했다.

### 6-2. 절차와 점수식

```
매 판단 주기마다
 ① 내 영토 목록 확보
 ② 후보 생성 — (내 영토 → 목표) 조합 + 여럿을 합쳐야 이기는 합공 조합
 ③ 점수 계산
 ④ 점수 0 이하는 전부 버리고(밑지는 공격은 하지 않는다),
    난이도에 따라 후보를 골라 실행. 이번 턴에 쓴 출발 영토는 중복 사용하지 않는다
```

```
score = 기본점 + 점령가치 + 생산가치 + 약점보너스 − 거리페널티 − 위험페널티

점령가치   = 목표 상한 × 가중치        # 큰 땅일수록 가치
생산가치   = 목표 생산량 × 가중치
약점보너스 = max(0, 보낼 병력 − 목표 병력) × 가중치
거리페널티 = 가장 가까운 출발지까지 거리 × 가중치
위험페널티 = 출발 영토가 안전선 밑으로 내려가는 만큼
```

**설계상 가장 마음에 드는 부분은 "빈집 털이" 로직을 따로 만들지 않은 것이다.** 목표가 방금 다른 곳을
공격하러 나가 병력이 비면 약점 보너스가 자연히 커지고 점수가 치솟는다. 별도 감지 로직이 필요 없다.

같은 방식으로 **"병력 모으기"도 명시적으로 만들지 않았다.** 점수 0 이하 후보를 전부 걸러 남는 게
없으면 이번 턴은 아무것도 하지 않는다. 그 사이 각 영토는 계속 생산하므로 결과적으로 모으는 상태가 된다.

### 6-3. 난이도

| 난이도 | 판단 주기 | 턴당 최대 실행 | 후보 선택 |
|---|---|---|---|
| 쉬움 | 6초 | 1 | 상위 절반 중 무작위 |
| 보통 | 3초 | 2 | 상위 3개 중 무작위 |
| 어려움 | 3초 | 2 | 항상 최고점 |

**난이도를 "가중치 조정"이 아니라 "선택 품질"로 표현한 것**이 핵심이다. 가중치를 흔들면 AI가
이상한 수를 두는 것처럼 보이지만, 선택 품질을 낮추면 **"괜찮은 수를 두는데 최선은 아닌"** 자연스러운
약함이 나온다.

판단 주기와 턴당 실행 수를 난이도에 넣은 것은 플레이 테스트 피드백이었다 — 영토가 많은 맵에서
AI가 여러 곳을 동시에 빠르게 공격하면 사람이 따라가기 벅차다.

### 6-4. 합공과 깎아먹기

- **합공** — 혼자서는 못 이기지만 가까운 영토 여럿(기본 3개)을 합치면 이기는 조합을 별도 후보로
  만든다. 플레이어의 다중 출발 공격과 같은 개념을 AI에도 적용한 것이다.
- **깎아먹기** — 단일 출발 후보는 완전 점령이 아니어도 보낼 병력이 목표의 60% 이상이면 후보로
  인정한다. 약점 보너스가 낮아 좋은 후보가 있으면 밀리지만, 대안이 없을 때는 이런 공격이라도
  실행해 여러 턴에 걸쳐 목표를 약화시킨다.

### 6-5. 가중치는 전부 인스펙터 노출

모든 가중치와 기본점을 에디터 노출 변수로 뒀다. 코드 수정 없이 조정할 수 있고, 실제 밸런싱이
코드 변경이 아니라 값 변경으로 끝난다.

## 7. 입력 — 멀티터치와 카메라 제스처의 공존

### 7-1. 드래그 경로 수집 — 상태를 배열로 들기

핵심은 **터치 하나가 가진 "선택된 영토"가 단일 값이 아니라 배열**이라는 점이다.

```
터치 상태 = { 선택된 영토들(배열), 현재 목표, 홀드 시간, 목표 위 체류 시간 }
터치 인덱스별로 각각 하나씩 보관 (마우스는 가상 인덱스)
```

| 이벤트 | 동작 |
|---|---|
| 터치 시작 | 내 영토면 새 상태를 만들고 배열에 담는다 |
| 드래그 중 | 지나간 지점이 아직 담기지 않은 내 영토면 배열에 추가. 아니면 목표 미리보기만 갱신 |
| 터치 종료 | 목표가 있으면 배열 전체가 출발지. 목표가 없으면 **배열의 마지막 원소를 목적지로** 삼고 나머지가 출발지 |
| 다른 손가락이 적/중립을 찍음 | 붙잡고 있던 모든 터치 상태의 영토를 그 목표로 동시 발진 |

**"목표가 없으면 마지막 원소를 목적지로"는 버그 수정에서 나온 설계다.** 처음에는 드래그가 아군
영토 위에서 끝나는 경우를 고려하지 않아, 공격받는 아군에게 지원을 보내려는 드래그가 아무 일도 하지
않았다. 실제 플레이 중 발견했다.

고친 결과가 뜻밖의 기능을 함께 낳았다 — **여러 영토에서 한 영토로 동시에 지원 보내기**가 공격 발진과
**완전히 같은 수집 로직**으로 처리된다. 특수 케이스를 없애려던 수정이 기능을 하나 더 준 사례다.

### 7-2. 카메라 제스처와 게임 조작의 충돌

이 게임은 **멀티터치를 이미 게임 조작에 쓰고 있다.** 그래서 "두 손가락이면 핀치"로 단순 매핑하면
기존 조작이 깨진다.

**해결: 역할은 누른 순간 아래에 있는 것으로 확정하고, 뗄 때까지 바뀌지 않는다.**

| 손가락이 눌린 곳 | 역할 |
|---|---|
| 내 영토 위 | 게임 조작. 이 손가락은 카메라를 절대 움직이지 않는다 |
| 빈 땅 | 카메라 조작(팬) |
| 중립·적 영토 위 | 잡고 있는 내 영토가 있으면 동시 발진 트리거, 없으면 팬 |

- **드래그 중에 판정이 뒤집히면** "공격하려던 손가락이 갑자기 화면을 옮기는" 사고가 난다.
  영토는 손잡이, 빈 땅은 테이블보라고 보면 된다.
- **핀치는 카메라 손가락이 2개 이상일 때만** 일어난다. "게임 손가락이라도 두 손가락이 벌어지면
  핀치로 승격"하는 규칙을 검토했다가 **버렸다** — 내 영토 두 개를 각각 잡고 다른 방향으로 드래그하는
  것은 **정상적인 동시 공격 조작**이고, 이걸 핀치로 오인하면 이미 조준한 공격이 취소된다. 손해가 더 크다.
- 판정은 입력 매니저가 한다. "이 좌표에 영토가 있나"는 입력 매니저가 아는 정보이고,
  **카메라는 넘겨받은 손가락만 처리하며 영토를 모른다**(책임 분리).

### 7-3. 줌 범위

최소 줌은 **맵 전체가 들어오는 값**으로 계산한다(뷰포트/맵 비율의 작은 쪽). 해상도와 맵 크기가
달라도 "다 보이는 상태"가 항상 최소 줌이 된다.

## 8. UI 시스템 — 재사용 가능한 모바일 UX 기반

UI가 전체 코드의 45%다. 화면을 늘릴 때마다 같은 문제를 다시 풀지 않도록 **공용 모듈**로 뽑아낸
것들이 이 장의 내용이다.

### 8-1. 버튼과 패널은 그림이 아니라 코드로 그린다

원본 버튼 이미지를 9슬라이스로 붙여봤다가 **되돌렸다.** 원본이 104×31인데 실제 버튼 높이는
26~56으로 제각각이라, 늘리고 줄이는 과정에서 테두리가 왜곡됐다.

대신 공용 스타일 모듈이 색·모서리·테두리·그림자를 코드로 생성한다. 크기가 어떻게 바뀌어도
테두리 두께가 일정하고, 팔레트를 한 곳에서 바꾸면 전 화면이 따라온다.

여기서 나온 작은 규칙 하나: **아이콘을 버튼 위에 얹을 때는 흰 실루엣을 쓴다.** 색 보정은 곱셈이라
어두운 그림을 밝게 만들지 못한다. 흰 그림을 두고 글자색으로 물들이면 **밝은 버튼에서는 어둡게,
어두운 버튼에서는 희게** 한 장으로 해결된다.

**인게임 화면도 같은 팔레트로 칠했다.** 모달만 바꾸면 인게임에 들어간 순간 옛 스타일로 돌아간다.
다만 맵 위에 상시로 뜨는 상단 칩은 **투명도를 남겼다** — 꽉 찬 배경으로 깔면 그 아래 지형이 가려진다.

### 8-2. 화면 방향 즉시 전환 — 되돌리는 코드를 손으로 쓰지 않는다

세로 배치는 앵커·오프셋·방향·정렬을 여러 노드에서 한꺼번에 바꾼다. **역함수를 손으로 쓰면 배치를
고칠 때 두 곳을 고쳐야 하고, 한쪽만 고치는 순간 세로 → 가로가 조용히 깨진다.**

**해결: 스냅샷.** 씬에 적힌 원래 값을 시작 시 한 번 찍어두고, 방향이 바뀌면 되돌린 뒤 세로면 다시
칠한다. 배치 코드가 늘어나도 되돌리는 쪽은 손댈 것이 없다.

```
방향 변경 →  스냅샷 복원  →  (세로면) 세로 배치 적용
```

플랫폼별로 경로가 갈린다:

| | 하는 일 |
|---|---|
| 모바일 | OS에 방향 전환을 요청한다(실제로 화면이 돌아간다) |
| 데스크톱 | 방향 전환을 지원하지 않으므로 **창 크기로 흉내낸다**(개발 확인용) |

데스크톱 경로에서 두 가지 함정을 만났다. ① **최대화된 창은 크기 변경 요청을 무시한다** — 창은
그대로인 채 콘텐츠 스케일만 세로가 되어 초광폭 뷰포트가 나온다. 그래서 크기를 바꾸기 전에 최대화를
먼저 푼다. ② 세로 기준 크기가 일반 모니터 높이에 안 들어가 비율대로 줄여 가운데에 놓는다.

**실기기에서는 회전이 비동기다.** 설정 변경 신호는 즉시 오고 실제 회전은 몇 프레임 뒤다. 그래서
로비와 스테이지 화면은 설정 신호뿐 아니라 **뷰포트 크기 변경 신호도 함께 구독한다.**

검증 기준도 정해뒀다: **가로 → 세로 → 가로 왕복 후 첫 가로와 픽셀이 같아야 한다.** 세로 배치가
남아 있으면 여기서 걸린다.

### 8-3. 모달은 화면에 맞춰 줄어든다

새 모달은 가로 기준으로 크기를 정했는데, 세로는 폭이 좁아 큰 패널이 잘려 나간다. 패널의 자식으로
붙는 공용 모듈이 화면이 바뀔 때마다 크기를 다시 계산한다.

> **패널을 위치 값으로 가운데 잡으면 안 된다.** 위치는 부모 사각형 해석에 따라 달라져, 부모가 아직
> 크기를 못 받은 순간에 넣으면 화면 밖으로 나간다. **앵커 0.5 + 오프셋 ±절반**으로 잡는다.

### 8-4. 가상 키보드 회피

안드로이드에서 채팅 입력을 누르면 키보드가 화면 아래 절반을 덮어 **입력 중인 글자도 방금 온 말도
보이지 않았다.** 공용 모듈이 감시 중인 입력 칸에 포커스가 있는 동안 대상을 키보드 높이만큼 위로 민다.

- **채팅은 창을 통째로 올린다.** 입력창만 올리면 방금 온 말이 안 보여 무엇에 답하는지 모른다.
  올릴 창은 **부르는 쪽이 알려준다** — 조상 노드를 훑어 찾게 했더니 입력 행에서 먼저 걸려 그 줄만
  올라갔다.
- **모달은 자동이다.** 공용 패널 생성기가 달아 주므로 친구 추가·길드 검색·신고·계정 연동이
  한꺼번에 해결됐다.
- **높이는 화면 픽셀 → UI 좌표로 환산한다.** 안 하면 고해상도 기기에서 두 배로 밀린다.
- 윗변이 화면 밖으로 나가지 않는 선까지만 민다.

### 8-5. 한글 조합 보호

한글은 자모를 모아 한 글자를 만들어서 **마지막 음절이 조합 중(pre-edit)으로 남아 있다.** 그 상태에서
다른 곳을 눌러 포커스가 빠지면 조합이 확정되지 않고 **취소**되어 마지막 글자가 사라진다. 엔터로
보내면 조합이 확정되므로 그때는 멀쩡하다 — **"간헐적"으로 보였던 증상의 정체가 이것이다.**

공용 모듈이 텍스트가 바뀔 때마다 **확정된 값의 그림자**를 남기고, 포커스가 빠진 뒤 글자가 줄었으면
되돌린다. 채팅·닉네임·길드(공지·초대·검색·생성)·친구 추가·계정 연동·신고에 모두 붙였다.

여기에도 함정이 하나 있어 규칙으로 남겼다: **코드가 값을 비울 때는 전용 초기화를 쓴다.** 그냥
텍스트를 빈 문자열로 지우면 그림자가 남아, 포커스가 빠지는 순간 방금 보낸 글이 되살아난다.

### 8-6. 신호를 구독하는 쪽은 "지금 상태"를 한 번 읽어야 한다

튜토리얼 첫 안내가 화면을 한 번 눌러야 나타나는 문제가 있었다. 스테이지 구성 중에 첫 단계 신호가
발사되는데 **그때 HUD는 아직 연결 전**이라 신호를 놓친 것이다.

HUD가 연결 직후 **현재 단계를 직접 읽어** 맞추도록 고쳤다. 연결 순서에 기대지 않으므로 다시 깨지지
않는다. 이 규칙은 프로젝트 여러 곳에 필요했고, 이후 신호 구독 코드의 기본 형태가 됐다.

## 9. 튜토리얼 — 읽고 넘기는 안내를 만들지 않는다

문구만 띄우면 읽지 않고 넘긴다. 그래서 **화면을 이끌고, 실제로 해봐야 넘어가게** 만들었다.

### 9-1. 단계 정의

한 단계는 `문구 / 스포트라이트 대상 / 손가락 데모 경로 / **요구 동작**`으로 구성된다.
요구 동작은 여섯 가지: 읽고 넘김 · **지정 경로로 실제 드래그** · 점령 · 대기 · 집결 · 레벨업.

- **지정 경로 드래그는 그 경로로 보냈을 때만 통과**시킨다. 아무 데나 보내고 넘어가면 수업이 안 된다.
  게임 매니저가 커맨드 제출을 신호로 방송하기 때문에 가능한 검사다(2-3 참조).
- **집결·레벨업은 드래그가 아니라 더블탭 메뉴로 들어와** 공격 신호로 잡히지 않는다. 그래서 두 명령
  전용 신호를 추가했다. 이게 없으면 "실제로 해봐야 넘어간다"는 원칙이 그 판에서만 깨진다.
- **입력 게이트** — 읽는 단계에서는 입력을 통째로 막는다. 안 막으면 넘기려고 누른 탭이 출정으로
  새서 배우기 전에 병력이 날아간다. 반대로 드래그를 요구하는 단계는 막지 않는다.

### 9-2. 연출 — 셰이더 재사용

어둡게 덮고 대상만 밝히는 스포트라이트는 **시야 안개 셰이더를 그대로 재활용했다.** 그 셰이더가
이미 "맵 전체를 덮는 사각형 + 원형 구멍 + 월드 좌표 계산"이라 정확히 같은 문제였다. 색만 더 진하게
바꿨다.

여기서 렌더링 함정을 하나 만났다. 그 셰이더는 색을 통째로 덮어쓰기 때문에 **같은 노드에서 경로와
손가락을 그리면 그것들까지 어두워진다.** 자식 노드로 분리하면 부모 머티리얼을 물려받지 않고 부모보다
나중에 그려져 위에 얹힌다.

### 9-3. 커리큘럼 구성

| 스테이지 | 주제 | 가르치는 것 |
|---|---|---|
| 1 | 기본 조작 | 드래그 공격 → 병력 숫자·절반 출정 → 보급선 + 다중 드래그 → 영토 레벨 |
| 2 | 영토 종류 | 생산 버프 → 이동 버프 → 상한 버프 → 내 대포 → 적 대포 |
| 3 | 전략 요소 | 집결·레벨업 → 강물 → 용암 → 시야 |

각 주제 뒤에 **반복학습 판**(안내 없이 같은 규칙을 한 번 더 쓰는 판)이 붙는다. 초반 판에서는 적이
아무 행동도 하지 않는다.

순서에도 의도가 있다. **중립 대포는 발사하지 않게 해서**, 먼저 안전하게 대포를 차지해 보고
그다음 판에서 적이 든 대포를 상대하게 했다 — **위험을 배우기 전에 쓸모를 배우는 순서**다.

## 10. 백엔드 계층 — 서버가 없어도 게임은 돌아간다

### 10-1. 계층 구조

```
UI (로비 / 프로필 / 길드 …)
      │  기능 단위로 부른다 ("내 프로필 읽어와", "길드 가입")
      ▼
기능별 서비스 (프로필 / 친구 / 길드 / 랭킹 / 신고 / 진행도 동기화 / 지급)
      │  경로와 payload만 만든다
      ▼
게이트웨이 (Autoload)                     ← 세션 + 요청 창구
      │  로그인 · 토큰 갱신 · 인증 헤더 · 인증 실패 재시도
      ├──────────► HTTP 계층  → REST · 서버 함수 호출
      └──────────► 소켓 계층  → Realtime
```

**게이트웨이는 "무엇을 읽는지" 모른다.** 테이블을 아는 것은 서비스 쪽이고, 게이트웨이는 세션과
전송만 책임진다. 그래서 서비스가 늘어도 게이트웨이는 그대로다.

HTTP는 요청마다 새 요청 객체를 만든다 — 재사용하면 요청이 겹칠 때 실패한다.

### 10-2. 원칙: 오프라인 우선

서버 설정이 비어 있어도, 서버가 죽어도, 비행기 모드여도 **싱글 콘텐츠는 끝까지 되어야 한다.**
무료 인프라는 일정 기간 무요청이면 자동 일시정지되므로 이건 이론적인 상황이 아니다.

그래서 **어떤 함수도 예외를 던지지 않고 결과 객체를 돌려준다.**

```
결과 객체 = { 성공 여부, 상태 코드, 데이터, 오류 코드 }
```

오프라인 여부는 플래그 하나로 UI에 알린다. **저장은 로컬이 먼저고 서버는 그 사본이다.**

### 10-3. 익명 로그인 → 계정 연동

첫 실행에서 회원가입을 요구하지 않는다. 익명으로 가입하고, **가입 즉시 DB 트리거가 프로필 한 줄을
만든다.** 클라이언트가 프로필을 만들게 하면 "가입은 됐는데 프로필이 없는" 상태를 앱 전체가 처리해야
한다 — 그 분기를 아예 없애는 것이 목적이다.

연동은 **새 계정을 만드는 것이 아니라 기존 계정에 인증 수단을 붙이는 것**이다. 사용자 식별자가
그대로라 진행도·길드·친구가 전부 따라온다.

**연동과 로그인은 다른 일이다.** 로그인은 계정을 갈아타는 것이라 이 기기의 진행도가 대체된다.
그래서 두 번 눌러야 확정되고, 그 뒤에는 동기화가 아니라 **일방향 내려받기**를 쓴다 — 양방향 비교를
쓰면 남아 있던 게스트 기록이 더 앞섰다는 이유로 **남의 계정에 덮어쓴다.**

화면에 찍는 연동 정보는 **로컬 값**을 본다(서버가 죽어도 프로필이 비지 않게). 실제 판단은 늘
서버 세션이 한다.

### 10-4. 권한 설계 — 행 단위 정책과 서버 함수의 경계

행 단위 보안 정책(RLS)은 "이 줄을 건드려도 되는가"만 판단한다. **정원 제한 · 한 명은 한 길드만 ·
마지막 관리자가 나가면 위임**은 여러 줄을 함께 봐야 하는 규칙이라 정책으로 표현할 수 없고,
클라이언트에서 검사하면 공개 키로 우회된다.

**그래서 이런 규칙은 전부 서버 사이드 함수로 모으고 테이블 직접 쓰기를 막았다.**
친구 추가·수락도 같은 이유로 서버 함수다 — 두 방향의 줄을 한 트랜잭션에서 맞춰야 한쪽만 남는
유령 관계가 생기지 않는다.

**반대 방향의 함정도 있었다.** 갱신은 조건에 맞지 않으면 거절이 아니라 **0줄을 바꾸고 성공 응답**을
준다. 그래서 권한이 갈리는 수정은 **반환된 행이 비었는지까지 확인**한다. 응답 코드만 보면 "성공했는데
아무것도 안 바뀐" 상태를 놓친다.

쿼리를 짜면서 실제로 걸렸던 것 셋:

| 증상 | 원인 | 대응 |
|---|---|---|
| 한글 검색이 깨진다 | 쿼리 문자열에 한글을 그대로 붙였다 | URI 인코딩 필수 |
| 조인이 모호하다고 거절된다 | 한 테이블을 두 방향으로 참조하는 관계 | 외래키 방향을 명시 |
| 삽입은 됐는데 권한 오류 | 삽입 후 되읽기가 읽기 권한을 요구한다 | 읽기 정책이 없는 테이블은 결과 반환을 끈다 |

### 10-5. 실시간 채팅 — 테이블을 쓰지 않는다

로비 채팅과 길드 채팅은 **브로드캐스트만** 쓴다. DB를 거치지 않으므로 저장 용량도, 쓰기 부하도,
권한 정책도 필요 없다. **흘러가는 것이기 때문이다.**

- **소켓은 하나다.** 토픽마다 소켓을 열면 동시 접속 한도를 사람 수의 배수로 태운다.
- **화면 두 개가 같은 스크립트를 쓴다.** 채팅 뷰는 방 이름과 노드 세 개(로그·입력·전송)만 받고
  씬 구조를 모른다. 그래서 길드 채팅을 새로 만들 필요가 없었다.
- **끊기면 알아서 다시 붙는다.** 모바일은 화면을 껐다 켜는 것만으로 소켓이 죽으므로 재연결은
  선택이 아니다. 붙어 있어야 할 방 목록을 들고 있다가 재연결 후 그대로 다시 구독한다.
- **모든 방을 떠나면 소켓을 닫는다** — 배터리와 동시 접속 한도를 아낀다.

### 10-6. 진행도 동기화 — 앞선 쪽 자동 채택

저장 파일 두 개(진행도 + 소유물)를 **한 덩어리 JSON으로** 올린다. 서버가 내용을 해석하지 않으므로
저장 포맷을 바꿔도 스키마를 건드리지 않는다.

**충돌 기준은 "클리어한 판 수" 하나뿐이다.** 서버가 나보다 많이 깼으면 내려받고, 아니면 올린다.
같으면 올린다(지금 켜져 있는 기기가 더 최신일 가능성이 높다).

세 가지 판단이 들어 있다.

- **재화를 합치지 않는다.** 진행도와 통째로 같이 움직인다. 최댓값이나 덧셈으로 합치면 두 기기를
  번갈아 켜는 것만으로 재화가 불어나는 **복제 구멍**이 생긴다.
- **유저에게 묻지 않는다.** 대부분은 이 상황을 이해하지 못하고, 물어봐야 "많이 한 쪽"을 고른다.
- **저장 파일과 서버가 같은 필드 표를 쓴다.** 상태를 내보내고 들여오는 함수를 공용으로 두었다 —
  필드 목록이 두 벌이면 반드시 한쪽만 늘어나 어긋난다. 채택할 때는 **두 Autoload를 함께** 갈아끼운다
  (하나만 바꾸면 "스테이지는 앞섰는데 재화는 예전 것"인 어긋난 상태가 남는다).

### 10-7. 랭킹

| 판 | 기준 |
|---|---|
| 싱글 | 싱글 랭킹 포인트 |
| 길드 | 길드 레벨(동점은 경험치) |

- **순위표는 서버 함수를 쓰지 않는다.** 읽기가 공개인 데이터라 클라이언트가 정렬·제한 쿼리로 바로
  가져온다. 서버 함수를 하나 더 두면 **정렬 규칙이 SQL과 클라이언트 두 곳에 생긴다.**
- **서버 함수가 필요한 것은 "내 순위" 하나뿐이다** — 그건 세어 봐야 안다. 셋을 한 번에 돌려준다
  (따로 부르면 왕복이 세 번이다). 길드에 안 속했으면 **0이 아니라 null**을 준다 — 0등은 없으므로
  받는 쪽이 "모른다"와 구분할 수 있다.
- **동점은 같은 등수다**(나보다 높은 사람 수 + 1). 1등이 둘이면 다음은 3등. **목록 순서를 그대로
  등수로 쓰면 동점자가 1·2등으로 갈려**, 서버가 세어 준 내 순위와 화면의 번호가 어긋난다.
  그러면 그 화면 전체가 못 믿을 화면이 된다.
- 50위 밖이면 목록에 없으므로 **내 순위를 아래에 따로 붙인다** — 이 화면을 여는 이유가 자기를
  찾는 것이기 때문이다.
- 정렬용 인덱스를 함께 넣었다. 없으면 유저가 늘수록 순위표가 전수 정렬이 된다.

## 11. 결제 — 클라이언트 응답을 믿지 않는 지급 설계

### 11-1. 플러그인을 만지는 자리는 하나다

```
상점 / 패스 화면
    ↓  상품 카탈로그  ← 가격·한도·지급 규칙의 주인
    ↓  결제 서비스(Autoload)   ← 스토어 플러그인을 아는 유일한 파일
    ↓
네이티브 플러그인 (Android / iOS)
```

플러그인이 바뀌거나 교체돼도 **고칠 자리가 하나로 남는다.** 그리고 백엔드와 같은 규칙으로 실패를
정상 흐름으로 다룬다 — 데스크톱에는 플러그인 자체가 없으므로, 사용 가능 여부가 false면 조용히 사유만
돌려주고 게임은 그대로 돈다. **에디터에서 상점을 열어도 멈추지 않는다.**

### 11-2. 신뢰 경계 — 성공은 "스토어가 결제를 받았다"까지다

**구매 응답을 믿고 재화를 늘리지 않는다.** 상품 종류에 따라 지급 경로가 갈린다.

| 상품 | 스토어 유형 | 지급 경로 |
|---|---|---|
| 재화 팩 | 소모품(재구매 가능) | **웹훅 → 서버 지급 큐 → 클라이언트 수령** |
| 패스권 | 비소모품(1회) | 권한(entitlement) 상태로 판정 |

### 11-3. 왜 지급 큐인가 — 동기화와 충돌하기 때문

이 구조에서 가장 중요한 제약이다.

진행도 동기화는 로컬 스냅샷으로 서버의 한 줄을 통째로 덮어쓰고, 채택 기준은 **클리어한 판 수
하나뿐**이다(10-6). 구매로는 그 점수가 오르지 않으므로 **다음 동기화에서 클라이언트가 항상 이기고,
서버가 넣은 재화가 옛 잔액으로 덮인다.**

그래서 서버는 **"줄 것"만 쌓고**, 잔액을 바꾸는 주체는 클라이언트 하나로 고정했다.

```
스토어 웹훅
   ↓  Edge Function (서명 검증)
지급 큐에 한 줄      ← 이벤트 식별자가 기본키 = 중복 방지의 전부
   ↓  로비 진입 시 수령 요청
클라이언트가 잔액을 늘린다
   ↓
평소대로 동기화 (충돌 없음)
```

- **중복 방지는 이벤트 식별자를 기본키로 두는 것으로 끝난다.** 같은 웹훅이 재전송돼도 두 번 쌓이지
  않는다.
- **수령은 "갱신하면서 반환하는" 한 문장**이다. 조회와 수령 표시를 두 문장으로 나누면 그 사이에
  같은 요청이 또 들어와 두 번 지급된다.

### 11-4. 사용자 식별자 일치

```
인증 사용자 id  ==  클라이언트 세션 id  ==  결제 플랫폼 사용자 id  ==  웹훅의 사용자 id
```

**이게 아니면 결제가 어디에도 도착하지 않는다.** 익명으로 초기화하면 결제 플랫폼이 자기 익명 id를
만들고, 웹훅이 와도 줄 사람을 찾을 수 없다. 그래서 세션 변경 신호를 구독해 계정이 바뀔 때마다
결제 쪽 로그인/로그아웃을 따라가게 했다.

### 11-5. 가격은 코드에 박지 않는다

**스토어가 준 현지 가격 문자열을 먼저** 쓰고, 못 받았으면 박힌 값으로 되돌아간다. 스토어는 지역·세금에
따라 다른 금액을 청구하므로 **화면에 뜬 값과 실제 청구액이 다르면 스토어 정책 위반**이다. 박힌 값은
데스크톱·오프라인에서 화면이 비지 않게 하는 대비책일 뿐이다.

### 11-6. 신호를 무한정 기다리지 않는다

플러그인 API가 전부 신호 기반이라 대기로 받는데, **응답이 안 오면 화면이 영원히 멈춘다.**
신호와 타이머 중 먼저 오는 쪽을 받는 경쟁 처리를 넣었다 — 결제는 300초(사용자가 스토어 창을 붙들고
있을 수 있다), 나머지는 20초.

**취소를 실패로 보여주지 않는다.** 사용자가 스스로 닫은 것이라 사과할 일이 아니다.

## 13. 검증 방법론

이 프로젝트에서 가장 신경 쓴 부분이다. **사람 눈으로 보기 전에 자동으로 확인할 수 있는 선을 최대한
끌어올렸다.**

### 13-1. 헤드리스 부팅 검증

엔진을 헤드리스로 실행해 로비와 인게임 씬을 각각 띄운다.

```
헤드리스 실행 → 로비 씬  → 지정 프레임 후 종료 → 스크립트 오류 0 확인
헤드리스 실행 → 인게임 씬 → 지정 프레임 후 종료 → 스크립트 오류 0 확인
```

**로비가 모달들을 미리 적재하므로 로비 부팅만으로 UI 스크립트가 거의 다 컴파일된다.** 화면 하나를
띄우는 것으로 34개 UI 스크립트의 문법·타입 오류를 잡을 수 있다.

**문법 검사 전용 모드는 쓰지 않았다.** 그 모드는 전역 상태를 등록하지 않아서 멀쩡한 스크립트까지
"식별자를 찾을 수 없음"으로 뱉는다 — 전부 거짓 양성이다. **거짓 양성이 나오는 검사는 곧 아무도 보지
않는 검사가 된다.**

로직까지 확인할 때는 임시 전역 스크립트를 붙여 단정을 돌린다. 이때 **사용자 저장 파일을 먼저
백업하고 끝나고 복원한다** — 테스트가 실제 진행도를 건드린다.

### 13-2. 콘텐츠 전수 검사

인접 규칙을 도입할 때, 이웃이 하나도 없는 영토는 **아무 공격도 오갈 수 없는 죽은 영토**가 된다.
그래서 실제로 쓰이는 **28판 전부의 좌표를 전수 검사**했다.

깨진 판은 4개였고 좌표만 옮겨 고쳤다.

| 판 | 문제 | 수정 |
|---|---|---|
| 초반 3판 | 영토 둘의 간격이 사거리의 2배 이상 | 간격 축소 |
| 1판 | 적 본진이 최근접 영토에서 사거리 밖 | 본진 위치 이동 |

검사 결과:

| 판 | 영토 | 간선 | 평균 차수 |
|---|---|---|---|
| 튜토리얼 24판 | 2~10 | 1~11 | 전부 연결 |
| 고정 맵 1 | 33 | 48 | 2.9 |
| 고정 맵 2 | 33 | 44 | 2.7 |
| 고정 맵 3 | 33 | 60 | 3.6 |
| 고정 맵 4 | 24 | 48 | 4.0 |

경계 사례도 기록해 뒀다 — 한 쌍이 사거리 경계값과 **정확히 일치**해 부동소수점 오차로 판정이 갈릴
수 있다. 어느 쪽이든 그 판의 연결성은 유지되므로 그대로 두되, **알고 남긴 것**과 **모르고 지나친 것**을
구분하기 위해 문서에 적었다.

### 13-3. AI 회귀를 수치로 비교

인접 제한이 AI를 얼마나 약하게 만드는지 감으로 말하지 않기 위해, **같은 맵·같은 난이도로 헤드리스
12,000프레임**을 돌려 비교했다.

| | 행동 횟수 | 60초 시점 영토 |
|---|---|---|
| 인접 제한 전 | 13회 | 4개 |
| 인접 제한 후 | 8회 | 3개 |

후보 공간이 (내 영토 × 목표)에서 (간선)으로 줄어든 만큼이다. **약해진 정도를 수치로 알고 있으면
튜닝이 추측이 아니라 조정이 된다.**

### 13-4. 설계 전에 실측한다

실시간 통신 구조를 정하기 전에, **프로토콜을 직접 구현해** 실제로 되는지부터 확인했다.

| 항목 | 값 | 판단 |
|---|---|---|
| 프로토콜 직접 구현(참가·브로드캐스트·하트비트) | 전부 정상 응답 | **된다** — 최대 리스크 해소 |
| TCP 연결 | 10ms | 리전이 가깝다 |
| REST 왕복 | 50ms | 충분 |
| **브로드캐스트 왕복(RTT)** | **중앙값 102ms** (최소 101 / 최대 123, 20/20 응답) | 목표 200ms 이하 |
| 초당 10건 × 50건 | **유실 0 / 순서역전 0** | 유선 기준 |

**RTT 102ms 중 네트워크는 10ms뿐이다** — 나머지는 파이프라인 지연이라 리전을 바꿔도 줄지 않는다.
병력이 목적지까지 몇 초 걸리는 장르라 이 값은 체감되지 않는다는 결론까지 함께 얻었다.

**측정 결과가 좋았다고 안전장치를 빼지는 않았다** — 유선에서 유실이 0이어도 모바일 회선은 다르므로
순번·복구 설계는 그대로 유지하기로 했다.

서버 규칙(권한 정책·서버 함수)도 익명 계정 2개로 **29가지 시나리오를 전수 확인**했다(실패 0).

## 14. 트러블슈팅 사례집

### 사례 1 — 원인 하나, 증상 넷 (실기기 전용 입력 버그)

**증상(보고된 것).** ① 아군 영토를 한 번만 탭해도 더블탭 메뉴가 열린다. ② 두 손가락 핀치 줌이
전혀 안 된다. **둘 다 데스크톱에서는 정상이고 실기기에서만** 발생했다.

**원인.** 프로젝트 설정의 "터치를 마우스로 에뮬레이트"(기본값 켜짐) 때문에 **첫 번째 손가락 하나가
터치 이벤트와 마우스 이벤트 두 벌로** 들어온다. 즉 손가락 하나가 **두 개로 보인다.** 이 설정은 끌 수
없다 — UI가 터치를 받는 통로가 그것이다.

**증상이 넷이었다.**

| 증상 | 메커니즘 | 보고 여부 |
|---|---|---|
| 단일 탭이 더블탭 처리 | 탭 등록이 같은 탭을 두 번 받는다 | 보고됨 |
| 핀치 무반응 | 같은 손가락 둘을 짝으로 잡아 거리가 0 → 최소 거리 조건에 걸려 배율 계산을 건너뛴다 | 보고됨 |
| 파병 비율이 이상하다 | 발진이 두 번 실행 → 50% 보내고 남은 것의 50%를 또 보내 실제 75% | **미보고** |
| 튜토리얼이 두 단계씩 넘어감 | 튜토리얼도 같은 탭을 두 번 받는다 | **미보고** |

**혼란스러웠던 지점.** 한 손가락 팬은 멀쩡했다. 우연이었다 — 두 "손가락"이 같은 좌표라 핀치의 중점
추적식이 팬과 같은 결과를 냈고, 거리가 0이라 배율만 안 바뀌었다.

**해결.** 마우스 경로는 애초에 데스크톱 확인용이므로 **모바일에서는 끊는다.** 데스크톱 테스트는
그대로 된다.

**남긴 규칙.** *터치와 마우스를 함께 처리하는 코드에서 **이벤트 하나가 한 동작이라고 가정하면
실기기에서만 두 번 실행된다.*** 이후 입력 코드를 쓸 때 기본 점검 항목이 됐다.

---

### 사례 2 — 셰이더에서 맵 전체가 균일하게 어두워짐

**증상.** 시야 안개를 켰는데 구멍이 하나도 뚫리지 않고 맵 전체가 똑같이 어두웠다.

**원인.** 셰이더에서 UV와 텍셀 크기로 월드 좌표를 구했는데, 이 사각형은 **텍스처 없는 도형**이라
두 값이 의미 없는 값이 된다. 구멍 계산이 전부 빗나갔다.

**해결.** 정점 단계에서 **정점 좌표를 varying으로 넘겨** 월드 좌표를 직접 받게 했다(노드가 원점에
있고 스케일이 없어 정점 좌표 = 월드 좌표).

**부수 효과.** 이렇게 고친 셰이더가 "월드 좌표 기준으로 구멍을 뚫는 오버레이"라는 재사용 가능한
도구가 되어, 튜토리얼 스포트라이트를 새로 만들지 않고 해결했다.

---

### 사례 3 — 병력이 지형을 통과해 버림

**증상.** 강 옆에 정상 배치된 영토에서 병력을 보내면 **강을 그대로 가로질렀다.**

**원인.** 장애물과 조금이라도 겹치는 격자 칸을 모두 막았더니, 칸 크기(40px)만큼 **과하게 번져**
정상 영토가 있는 칸까지 막혔다. 출발 칸이 막히면 A*가 빈 경로를 주고, 빈 경로면 직선으로 되돌아간다.

**해결.** **칸 중심이 장애물 안에 들어올 때만** 막도록 바꿨다.

**교훈.** 안전장치(빈 경로면 직선 복귀)가 있으면 **버그가 크래시가 아니라 규칙 위반으로 나타난다.**
안전장치는 필요하지만, 그것이 발동했다는 사실을 알 방법도 함께 있어야 한다.

---

### 사례 4 — 지원 병력 드래그가 아무 일도 하지 않음

**증상.** 공격받고 있는 아군 영토에 지원을 보내려는데 드래그가 먹히지 않았다. **실제 플레이 중** 발견.

**원인.** 드래그가 지나간 내 영토는 "출발지 배열"에만 담고 있었고, **드래그가 아군 영토 위에서 끝나는
경우**를 고려하지 않았다. 목표가 끝내 정해지지 않아 아무 명령도 나가지 않았다.

**해결.** 종료 시 목표가 없으면 **배열의 마지막 원소를 목적지로** 삼는다.

**뜻밖의 소득.** 이 수정으로 **여러 영토 → 한 영토 동시 지원**이 공격 발진과 완전히 같은 로직으로
가능해졌다. 특수 케이스를 없애는 방향으로 고치면 기능이 따라오는 경우가 있다.

---

### 사례 5 — 무한 파밍 구멍 (경제 설계 결함)

**증상.** 코드는 정상인데 **일부러 바로 지면 재화를 무한히 얻을 수 있었다.**

**원인.** 두 규칙이 각각은 타당한데 겹치면 구멍이 됐다.
① "자유 대전은 패배에도 보상이 나간다"(플레이 동기 유지)
② "도전 실패 시 하트를 반환한다"(진입 비용 보호)
→ 소모 0으로 보상만 반복 획득 가능.

**해결.** 자유 대전은 하트를 반환하지 않는다. **중도 이탈도 같은 규칙**으로 처리했다 — 한쪽만
막으면 "지기 전에 나가면 하트가 남는다"는 우회로가 그대로 남는다.

**교훈.** 경제 구멍은 코드 리뷰가 아니라 **규칙 두 개를 곱해 봐야** 보인다. 이후 보상·소모 규칙을
추가할 때는 기존 규칙과의 조합을 먼저 확인했다.

---

### 사례 6 — 릴리스 서명이 로컬 도구 체인 때문에 실패

**증상.** 릴리스 서명 도구가 "적합한 Java를 찾을 수 없음"으로 실패. Java는 정상 설치돼 있었다.

**원인.** 엔진이 대상 SDK와 맞는 빌드 도구를 못 찾아 **구버전으로 폴백**했는데, 그 버전의 서명
스크립트는 `java -version` **출력 문자열을 파싱**해 Java를 찾는 방식이었다. 이 PC의 출력 앞에는
다른 도구가 심어둔 환경변수 안내와 경고 두 줄이 먼저 나와 **파싱이 깨졌다.**

**시도했지만 안 된 것.** 환경변수를 지우고 Java 경로를 바꿔도 소용없었다 — 그 스크립트는 네이티브
탐색기로 Java를 찾기 때문이다.

**해결.** **대상 SDK와 맞는 빌드 도구를 설치**했다. 신형 서명 스크립트는 버전 문자열을 파싱하지 않고
환경변수를 그대로 쓴다.

**교훈.** 도구 체인 문제는 **내가 준 입력이 아니라 도구가 고른 경로**를 봐야 할 때가 있다. 폴백이
조용히 일어나면 증상은 엉뚱한 곳에서 나타난다.

---

### 사례 7 — 규칙은 만들었는데 화면에 단서가 없었다

**증상(피드백).** ① 사거리 100이 어디까지인지 알 수 없어 "여기 먹으면 보급이 이어지나"를 눈대중해야
한다. ② 병력이 상한에 도달하면 생산이 멈추는데(= 낭비) 그 신호가 화면에 없다.

**해결.**
① 사거리 안의 모든 쌍을 아주 흐린 점선으로 그린다(5-1의 정보 유출 검토 포함).
② 병력 숫자를 80% 이상 노랑 / 100% 빨강으로 칠한다.

**여기서 만난 렌더링 문제.** 보급 끊김 표시가 이미 라벨의 색 보정을 쓰고 있었다. 그래서 경고색은
**글꼴 색**을 쓰도록 갈랐다 — 둘이 곱해지므로 "보급이 끊긴 채 꽉 찬" 영토는 **흐린 빨강**이 되어
**두 정보가 동시에 읽힌다.** 같은 채널을 두 정보가 쓰면 하나가 다른 하나를 지운다.

**적용 범위도 규칙으로 정했다.** 중립은 생산을 안 하니 "낭비 중"이 성립하지 않아 제외하고,
**적 영토는 포함**한다 — "적이 꽉 찼다 = 곧 나온다"는 유용한 정보다.

### 사례 8 — 컴파일이 되지 않는 언어 제약들

GDScript의 정적 타입 정책 때문에 초기에 반복해서 부딪힌 것들이다. 전부 규칙으로 정리해 문서에 남겼다.

| 문제 | 원인 | 대응 |
|---|---|---|
| 씬 트리로 얻은 참조에서 커스텀 멤버 접근 실패 | 정적 타입이 기본 노드 타입으로 추론된다 | 클래스 이름을 선언하고 참조 타입을 명시 |
| 전역 수학 함수 결과를 받으면 경고(=에러) | 반환 타입이 가변형이다 | float 전용 함수로 전면 교체 |
| 배열 필터 결과의 타입 보장이 불확실 | 정적 반환 타입 추정이 어렵다 | 반복문으로 직접 필터링, 복제 결과는 타입을 명시해 받는다 |
| 이름 충돌로 파서가 막힘 | 노드 내장 프로퍼티/메서드와 이름이 겹친다 | 도메인 용어로 개명(소유 진영 등), 서버 함수 호출자도 개명 |
| 여러 줄 문자열이 프로젝트 전체를 못 열게 함 | 일반 문자열에 실제 줄바꿈을 담을 수 없다 | 이스케이프 사용 |
| 중첩 타입 컬렉션 미지원 | 사전 값에 타입 배열을 쓸 수 없다 | 값 타입은 열어 두고 꺼낼 때 타입을 지정해 받는다 |

**교훈.** 언어 제약은 우회하기보다 **규칙으로 만들어 문서화**하는 편이 빨랐다. 같은 함정을 두 번
만나지 않는 것이 개별 우회보다 이득이 컸다.

## 15. 설계 판단 기록 — 일부러 하지 않은 것들

포트폴리오에서 더 말하고 싶은 부분이다. **무엇을 만들었는가보다 무엇을 만들지 않기로 했는가**가
설계의 실체라고 생각한다.

| 하지 않은 것 | 이유 |
|---|---|
| 인접하지 않은 출발지의 **자동 중계** | 편하지만 "모을까 / 지금 칠까"라는 결정 자체를 없앤다. 그 결정이 인접 규칙으로 얻으려던 전략성의 본체다 |
| 게임 손가락의 **핀치 승격** | 영토 두 개를 각각 잡고 다른 방향으로 끄는 것은 정상 조작이다. 핀치로 오인하면 조준한 공격이 취소된다 — 손해가 더 크다 |
| 보급·시야 모듈의 **캐시 공유** | 같은 식·같은 입력이라 결과가 동일한데, 캐시를 쓰려면 두 모듈에 새 의존을 넣어야 한다. 얻는 게 성능뿐이라 값이 안 맞는다 |
| 전선 영토의 **감쇠 예외** | 최전선이 상한을 넘겨 버티는 요새가 되어, 상한 통일로 없앴던 "웅크리기"가 되살아난다 |
| 결과 화면 프레임 이미지 유지 | 원본 최소 크기에 못 미쳐 이미 찌그러져 있었다. 코드 생성 스타일로 바꾼 것이 개선이었다 |
| 동기화 충돌 시 **사용자에게 묻기** | 대부분은 상황을 이해하지 못하고, 물어봐야 "많이 한 쪽"을 고른다 |
| 재화의 **병합(최댓값/덧셈)** | 두 기기를 번갈아 켜는 것만으로 재화가 불어나는 복제 구멍이 생긴다 |
| 순위표용 **서버 함수** | 읽기가 공개인 데이터라 정렬 규칙이 SQL과 클라이언트 두 곳에 생길 뿐이다 |
| 채팅 **DB 저장** | 흘러가는 것이다. 저장 용량·쓰기 부하·권한 정책이 전부 불필요해진다 |
| 커맨드 **큐/틱 처리 선구현** | 검증할 대상이 없는 상태에서 만들면 실제 요구와 어긋난다. 값이 확실한 경계(공유 진입점)만 취했다 |
| 유료 재화로 **전투력 판매** | 전투력을 직접 파는 순간 되돌리기 어렵다. 판매 대상은 코스메틱과 편의로 한정했다 |
| 레벨업 보상에서 **재화 지급** | 레벨업이 소모처가 아니라 파밍처가 되어 상점의 역할이 사라진다 |

## 16. 회고

### 잘한 것

- **문서를 먼저 쓰고 그대로 지킨 것.** 3주 동안 기능이 계속 늘었는데도 구조가 무너지지 않았다.
  특히 "왜 그렇게 했는지"를 변경 이력에 남긴 것이 나중에 같은 판단을 반복하지 않게 해줬다.
- **이미 있는 것을 먼저 찾은 것.** 인접 그래프(기존 보조선), 튜토리얼 스포트라이트(기존 셰이더),
  실전연습 맵(기존 고정 맵), 길드 채팅(기존 채팅 뷰) — 네 번의 큰 기능이 새 코드를 거의 쓰지 않고
  나왔다.
- **감이 아니라 수치로 판단한 것.** 맵을 정량 검증하고, AI 회귀를 시뮬레이션으로 재고, 통신을
  설계 전에 실측했다. "괜찮아 보인다"로 넘긴 것이 나중에 문제가 되는 일을 크게 줄였다.
- **실패를 정상 흐름으로 다룬 것.** 서버 호출도 결제도 예외를 던지지 않는다. 그 덕분에 오프라인·
  미설정·플러그인 부재가 전부 분기 하나로 흡수되고, 에디터에서 모든 화면을 열어볼 수 있다.

### 어려웠던 것

- **실기기에서만 나는 문제.** 데스크톱에서 정상인 코드가 실기기에서 다르게 도는 경우(입력 중복,
  키보드, 회전 비동기)가 반복됐다. 이후로는 플랫폼별 경로가 갈리는 코드를 쓸 때 "이 가정이 실기기에서도
  참인가"를 먼저 확인하게 됐다.
- **규칙 하나를 바꾸면 콘텐츠가 흔들린다.** 인접 규칙 도입이 28판의 좌표 검사로 이어졌다. 데이터가
  쌓인 뒤의 규칙 변경 비용을 체감했고, 그래서 이후 규칙은 **먼저 전수 검사 방법부터** 정하고 손댔다.
- **같은 표현 채널에 두 정보를 태우면 하나가 지워진다.** 색 보정 하나에 보급 상태와 상한 경고를
  같이 태우려다 겪었다. 표시 채널도 자원으로 보고 배분해야 한다는 것을 배웠다.

### 다시 한다면

- **입력 계층은 처음부터 플랫폼별 경로를 명시**했을 것이다. 나중에 갈라내는 것보다 처음부터 갈라두는
  편이 싸다.
- **검증 스크립트를 더 일찍** 만들었을 것이다. 헤드리스 부팅 검증은 도입한 순간부터 매 작업의
  기본 절차가 됐는데, 그 전 구간에서는 컴파일 오류를 사람이 발견했다.
